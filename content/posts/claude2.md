前两篇我们分别聊了：

- CLAUDE.md 不是项目百科全书，而是 AI 工作时必须知道的项目规则。

- 真正值得写入 CLAUDE.md 的，是 AI 难以自行确认，但又会影响工作结果的信息。

但还有一个更现实的问题：

如果一个项目已经使用 Claude Code 或 Codex 几个月甚至几年，里面的 CLAUDE.md 往往已经变成什么样？

通常是这样：

```md
# CLAUDE.md

## Project Overview

项目介绍……

## Architecture

架构说明……

## Rules

不要这样……
必须这样……

## History

以前因为某个问题增加了一条规则……

## Notes

一些临时说明……
```

最开始每一条规则都有意义。

但随着时间过去：

* 项目架构变了；
* 团队流程变了；
* 模型能力提升了；
* 某些问题已经不存在了；

这些规则却仍然留在那里。

最后：

> CLAUDE.md 有可能不再帮助 AI，反而开始增加 AI 的判断成本。

真正的问题不是文件长，而是：

* 无效；
* 过期；
* 冲突；
* 低价值。

所以，维护 CLAUDE.md 的重点不是不断增加规则。

而是：

> **定期审查，让它保持准确、精简和有效。**

![](https://cdn.jsdelivr.net/gh/visiongem/BlogImages@master/ai/2026/claude2.png)

---

## 一、为什么 CLAUDE.md 需要定期健检？

很多人维护代码，但很少维护 AI 指令。

代码会经过：

* Code Review；
* 测试；
* 重构；
* 删除旧逻辑。

但是 CLAUDE.md 经常是：

```
创建
 ↓
增加规则
 ↓
继续增加规则
 ↓
没人删除
```

最后形成一种类似“规则债务”（Instruction Debt）的问题：

规则越来越多，

但真正有效的信息越来越少。

---

### 什么是规则债务？

假设一条规则：

```md
不要使用 OldApi。
```

它最开始存在的原因：

```text
OldApi 有 bug。
```

半年后：

* OldApi 已经删除；
* 新 API 已经稳定；
* 项目完全迁移完成。

但是 CLAUDE.md 仍然存在：

```md
不要使用 OldApi。
```

这时候它已经不是帮助。

而是垃圾信息。

因为 AI 每次看到它，都需要判断：

> 这条规则现在还适用吗？

---

所以：

一条过期规则的成本包括：

* 占用上下文；
* 增加判断成本；
* 可能造成错误决策。

---

## 二、健检之前，先不要修改

很多人看到一份很长的 CLAUDE.md，第一反应：

> 删除一半。

但这是危险的。

因为不知道这些规则为什么存在。

正确流程应该是：

```
读取现状
 ↓
理解规则来源
 ↓
验证是否有效
 ↓
决定保留、修改、迁移或删除
```

不要：

```
觉得没用了
 ↓
直接删除
```

---

## 三、第一步：给每条规则建立档案

打开 CLAUDE.md。

不要马上改。

先把规则分类。

例如：

| 规则             | 目的     | 来源      | 证据                  | 建议 |
| -------------- | ------ | ------- | ------------------- | -- |
| 禁止修改 generated | 防止代码覆盖 | 历史问题    | 仍存在生成流程            | 保留 |
| 使用 Kotlin      | 项目介绍   | /init生成 | 代码可发现              | 删除 |
| API 修改同步 Mock  | 防止遗漏   | 多次错误    | 仍手动同步（待验证）         | 保留 |
| 当前版本 2.3.1     | 临时信息   | 手动添加    | 信息已过期              | 删除 |

---

每条规则至少回答：

### 1. 为什么存在？

例如：

```md
不要直接修改 generated/
```

原因：

```
修改后会被重新生成覆盖。
```

---

### 2. 谁需要知道？

例如：

```
所有开发者
```

还是：

```
只有修改支付模块的人
```

---

### 3. 如果删除，会发生什么？

例如：

删除：

```
API 修改同步 Mock
```

可能导致：

```
测试数据长期不同步。
```

风险较高。

---

## 四、第二步：判断规则是否应该删除

删除一条规则之前，需要证据。

不要凭感觉。

---

### 证据一：代码证据

检查：

> 规则描述的问题是否仍然存在？

例如：

规则：

```md
禁止使用 Retrofit Callback。
```

检查项目：

如果已经全部迁移：

```kotlin
suspend fun request()
```

不存在 Callback。

那么：

这条规则可能已经失效。

---

### 证据二：文档证据

检查：

* README；
* 架构文档；
* 开发规范；
* 发布流程。

例如：

CLAUDE.md：

```md
数据库修改必须手动执行 migration。
```

但是最新文档：

```text
数据库 migration 已接入自动化流程。
```

那么旧规则需要更新。

---

### 证据三：实际使用证据

看最近一段时间：

这条规则是否仍然解决问题？

例如：

过去：

```
Claude 经常忘记更新 Mock。
```

所以增加：

```md
修改 API 必须同步 Mock。
```

但是半年后：

项目已经自动生成 Mock。

那么这条规则可能可以删除。

---

## 五、第三步：不是所有删除都是删除

很多内容不是没价值。

只是放错地方。

这是 CLAUDE.md 健检最重要的一步：

> 内容分流。

---

### 类型一：项目事实

例如：

```md
项目使用 Kotlin。
项目包含 app 模块。
项目使用 Compose。
```

建议：

删除。

因为：

AI 可以从代码发现。

---

### 类型二：目录规则

例如：

```md
frontend 页面修改后必须执行截图测试。
```

但是：

项目还有：

```
backend/
android/
scripts/
```

这些地方根本不需要。

那么：

不要放根目录 CLAUDE.md。

应该放：

```
frontend/CLAUDE.md
```

或者：

```
.claude/rules/
```

---

### 类型三：复杂流程

例如：

发布流程：

```
1. 修改版本号
2. 创建 Tag
3. 上传测试包
4. 执行自动化测试
5. 发布
6. 通知团队
```

这种不应该每次任务都加载。

更适合：

Skill。

例如：

```
release-skill
```

需要发布时：

再调用。

---

### 类型四：必须阻止的问题

例如：

```
禁止提交 API Key。
```

这类规则：

不要只依赖 CLAUDE.md。

因为：

AI 提醒 ≠ 强制执行。

例如：

“不要提交 API Key”

适合告诉 AI。

但：

“绝对禁止 API Key 进入仓库”

应该由自动化系统保证。

因为安全边界不能依赖模型记忆。

应该交给：

* Git Hook；
* CI；
* 安全扫描工具。

---

## 六、第四步：检查规则是否重复或者冲突

随着项目发展，经常出现：

```md
规则 A：

所有接口必须使用 Retrofit。


规则 B：

新接口优先使用 Ktor Client。
```

两个规则同时存在。

AI 会怎么办？

它只能猜。

---

所以健检时需要检查：

### 重复

例如：

```md
修改接口后运行测试。
```

出现三次。

保留一次即可。

---

### 冲突

例如：

旧架构：

```md
Repository 负责所有数据处理。
```

新架构：

```md
UseCase 负责业务逻辑。
```

需要重新整理。

---

## 七、第五步：重新设计 CLAUDE.md

经过清理后，一个健康的 CLAUDE.md 通常不会很长。

例如：

```md
# Project Rules

## Architecture

- UI 层禁止直接访问 DataSource。
- 新功能必须遵循 Feature 模块结构。

## Business Rules

- 金额统一使用分存储。
- 支付状态只能由服务端确认。

## Workflow

- API 修改必须同步更新 Mock。
- 数据库 Schema 修改必须创建 Migration。

## Verification

- 根据修改范围运行对应测试。

## References

- API 文档：
docs/api.md

- 发布流程：
docs/release.md
```

重点：

没有项目介绍。

没有目录说明。

没有技术栈列表。

只有：

> AI 不知道，但必须知道的事情。

---

## 八、建立长期维护机制

CLAUDE.md 不是一次整理完成。

应该建立周期性维护。

例如：

每个月：

检查：

* 是否有过期规则；
* 是否有重复规则；
* 是否有新的高频错误。

每次大版本升级：

检查：

* 架构规则是否变化；
* 工具链是否变化；
* 工作流程是否变化。

---

可以建立一个简单习惯：

每当增加一条规则时，同时记录：

```md
为什么增加：

解决什么问题：

什么时候可以删除：
```

例如：

```md
禁止直接修改 generated 文件。

原因：
过去多人误修改导致线上问题。

删除条件：
生成流程完全自动化后。
```

这样未来删除会容易很多。

---

## 九、使用健检 Prompt 自动分析

可以让 Agent 自己帮助审查：

```text
请审查当前项目中的 CLAUDE.md。

目标：

1. 找出过时规则；
2. 找出重复规则；
3. 找出应该迁移到其他位置的内容；
4. 找出缺失的重要隐性知识。

请不要直接修改。

先输出：

|规则|问题|证据|建议|
|---|---|---|---|

建议只能是：

- 保留
- 修改
- 删除
- 移动到 Rules
- 移动到 Skill
- 移动到 Hook/CI
- 待验证

如果建议删除，请说明删除依据。

如果证据不足，请标记为“待验证”。

不要因为规则看起来冗余就删除。
```

注意：

不要让 AI 直接删除。

因为：

删除规则本身也需要判断。

---

## 十、本篇真正需要记住的 5 句话

### ① CLAUDE.md 最大的问题不是少，而是旧。

过期规则比没有规则更危险。

---

### ② 删除规则需要证据。

不要凭感觉清理。

---

### ③ 内容应该放在正确的位置。

CLAUDE.md、Rules、Skill、Hook、CI 各自负责不同事情。

---

### ④ 高频错误值得沉淀。

一次错误不用记录。

重复错误才值得变成规则。

---

### ⑤ 好的 CLAUDE.md 是不断进化的。

它不是写完的一份文档。

而是一套随着项目变化不断调整的 AI 工作协议。

---

到这里，我们解决了：

* “规则应该写什么”；
* 以及“旧规则如何清理”。

但还有一个更大的问题：

所有规则是不是都应该放 CLAUDE.md？

答案是：不一定。

下一篇我们进入 AI Agent 工程化设计：

* CLAUDE.md 的边界在哪里；

* Skill 为什么适合长流程；
* Hook 为什么比提示词更可靠；
* 如何设计一套完整的 Agent 工作体系。
