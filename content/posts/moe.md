## 一、什么是 MoE？一句话 + 一个比喻

**MoE（Mixture of Experts，混合专家）** 是一种神经网络架构设计模式，核心思路就一句话：

> **把一个大模型拆成多个"小专家"，每个 token 只激活其中少数几个，而不是全部。**

打个比方：

- **传统 Dense 模型** = 一个全科医生，无论头疼、脚疼、肚子疼，都找他一个人看。他得什么都懂，知识全装在一个脑子里。
- **MoE 模型** = 一家综合医院，有内科、外科、儿科、皮肤科等各个科室（专家），门口有个分诊台（门控网络），根据你的症状把你分到最合适的 1~2 个科室。

这样一来，医院的总医生数量（总参数）可以很大，但你每次看病只需要见其中一两位（激活参数少）。**总知识容量和单次服务成本——解耦了。**

## 二、MoE 是怎么工作的？

### 2.1 先看一张结构图

Dense Transformer 的 FFN 层：

```
        Token
          │
          ▼
        FFN（所有参数都参与计算）
          │
          ▼
        Output
```

MoE 替换后：

```
        Token
          │
          ▼
       Router（门控网络，轻量级）
       ╱    │    ╲
      ▼     ▼     ▼
  Expert1 Expert2 Expert3  ...  ExpertN
      │           │
      └─────┬─────┘
            ▼
          Merge（加权合并）
            ▼
         Output
```

### 2.2 三大核心组件

| 组件 | 作用 | 技术形态 |
|---|---|---|
| **专家（Expert）** | 独立的小型前馈网络 | 通常就是若干个 FFN（MLP） |
| **门控网络（Gate / Router）** | 对每个 token 打分，决定发给哪几个专家 | 一个线性层 + softmax/sigmoid |
| **稀疏激活（Sparse Activation）** | 只选 top-k 个专家参与计算 | k 通常为 1~8，其余专家"休眠" |

### 2.3 一次前向传播的完整流程

```
输入 token x
    ↓
Router(x) → 对 N 个专家分别打分 → 选分数最高的 top-k
    ↓
Expert_i(x) + Expert_j(x) → 按路由权重加权求和
    ↓
输出送入下一层
```

**关键点**：Router 本身非常轻量（就是一个线性层），几乎不增加计算成本。真正的计算量集中在被激活的少数几个专家身上。

## 三、为什么偏偏是 FFN？MoE 最关键的架构选择

很多读者第一次接触 MoE 时最大的疑问是：

> 为什么被替换的总是 FFN？
>
> 为什么不是 Attention？为什么不是整个 Transformer Block？

这个选择不是随意的，而是由 Transformer 内部的分工决定的。

### 3.1 Attention 和 FFN 在 Transformer 里的角色完全不同

```
        Attention（信息交换层）
              │
              ▼
           Add & Norm
              │
              ▼
        FFN（知识存储层）
              │
              ▼
           Add & Norm
              │
              ▼
        （进入下一层）
```

### 3.2 Attention 负责"通信"——不该被拆分

Attention 做的是**全局信息交换**：

```
"苹果很好吃"    →   Attention 让 "苹果" 看到 "好吃"，判断是水果
"苹果发布了新手机" →   Attention 让 "苹果" 看到 "手机"，判断是公司
```

所有 token 之间需要互相看、互相通信。这个过程天然是**密集的、全局的**，很难稀疏化——如果每个 token 只跟少数几个 token 做 attention，信息交换就不完整了。

### 3.3 FFN 负责"知识存储"——最适合拆成专家

大量研究（Geva et al., 2020; Dai et al., 2023; Qiu et al., 2024）已经证明：**Transformer 的 FFN 层本质上是一个键值记忆库（Key-Value Memory）**。

通俗理解：

- FFN 的第一层：**"模式检测器"（Key）**——识别输入是什么类型的信息
- FFN 的第二层：**"知识输出器"（Value）**——根据识别结果调取存储的知识

举个例子，当你问模型"法国的首都是什么"，FFN 里某个神经元组合会识别出"这是在问国家首都"，然后调取"巴黎"这个答案。

**这就是为什么 MoE 天然适合替换 FFN**：

```
知识库（FFN）
    ↓ 拆分成多个专家
专家 A：擅长编码/编程知识
专家 B：擅长数学/逻辑推理
专家 C：擅长多语言翻译
专家 D：擅长事实性知识
...
```

> **一句话总结：Attention 负责"让 token 之间聊天"，FFN 负责"从记忆中提取知识"。MoE 的本质，就是把知识记忆库拆成多个分库，各管一摊。**

## 四、专家真的会自动分工吗？

这是 MoE 最迷人的问题之一：我们并没有告诉专家"你负责数学，你负责代码"——它们是自己学会分工的。

### 4.1 证据一：句法感知——专家学会了"语法"

COLING 2025 一篇论文 *Part-Of-Speech Sensitivity of Routers in MoE Models* 做了这样一个实验：训练一个分类器，**只看 token 被路由到了哪些专家（不看 token 内容本身）**，来预测这个词的词性。

结果：**准确率高达 79%~88%**（在 Mixtral、DeepSeekMoE、DBRX、Qwen1.5-MoE 等 6 个模型上验证）。

这说明：路由路径本身就编码了丰富的句法结构信息。专家虽然没有"数学专家""英语专家"的标签，但它们对词性（名词、动词、形容词等）表现出了显著的选择偏好。

### 4.2 证据二：相邻 token 倾向同一专家

Mixtral 论文发现了一个有趣的现象：**相邻的 token 大概率被路由到同一个专家**。

- 随机分配的话，相邻两 token 选同一个专家的概率 ≈ 12.5%（8 选 1）
- Mixtral 实际的值**远高于随机基线**，在中间层尤其明显

这意味着：Router 倾向于把语义相关的连续 token 交给同一个专家处理——这是一种隐式的语义连续感知。

### 4.3 证据三：深层专家多样性更高

NAACL 2025 的研究 *A Closer Look into MoEs* 对 Mixtral、DeepSeekMoE、Grok-1 做了系统分析，发现：

| 层深度 | 专家多样性 |
|---|---|
| 浅层（前几层） | 专家输出相似度高，分化不明显 |
| 中间层 | 输出差异大，专业化程度最高 |
| 最后一层 | 再次收敛，输出趋同 |

这说明**专家的专业化主要发生在中间层**——浅层处理通用特征，深层做最终融合，中间层才是专家"各显神通"的地方。

### 4.4 但也要诚实：专家并不像你想象的那么"专"

一个重要的事实是：**专家的"专"更多体现在句法/结构层面，而不是主题层面**。

Mixtral 论文做了严格的消融实验，把 arXiv 论文、生物学文献、哲学论文、GitHub 代码分别喂给模型，发现**专家在不同领域的分布几乎一样**——并没有出现"专家 A 专做代码、专家 B 专做数学"这种干净的分工。

真正驱动路由差异的，是**token 层面的句法和结构特征**（比如标点符号、缩进、LaTeX 语法、代码关键字等），而不是高层的语义主题。

> **所以更准确的描述是：专家学会了按"token 是什么类型的东西"来分工，而不是按"token 在聊什么话题"来分工。这是一个语法层面的专业化，而非语义层面的专业化。**

## 五、GPT-4 为什么要用 MoE？

### 5.1 GPT-4 到底长什么样？（注意：从未官方确认）

OpenAI 从未公布 GPT-4 的架构。以下数据来自第三方分析和业内人士的推测，最广为引用的是 SemiAnalysis（Dylan Patel & Gerald Wong）在 2023 年 7 月的调查报告：

| 项目 | 推测数据 |
|---|---|
| 总参数 | ~1.8 万亿（1.8T） |
| 专家数量 | 16 个 |
| 每次激活专家数 | 2 个（top-2 routing） |
| 每 token 激活参数 | ~2800 亿（280B） |
| 层数 | 120 层 |
| 训练数据 | ~13 万亿 token |
| 训练硬件 | ~25,000 张 A100，跑 90-100 天 |
| 训练成本 | ~6300 万美元 |

> ⚠️ **免责声明**：以上全部数据均来自第三方推测，OpenAI 从未官方确认。George Hotz（Comma.ai 创始人）在 2023 年 6 月 Latent Space 播客中给出的版本是"8 专家 × 220B"，与 SemiAnalysis 口径不同。GPT-4 的架构至今仍是行业最著名的"公开秘密"之一。

### 5.2 为什么 GPT-4 选择 MoE？三个核心原因

**原因一：算力-知识密度的最优解**

如果 GPT-4 做成一个 1.8T 的 Dense 模型，每个 token 的前向传播就要跑满全部 1.8T 参数。按这个体量，推理成本根本不是商业 API 能扛住的。

用 MoE 之后：总参数 1.8T，但每次只激活 ~280B。**知识容量是超大模型级别的，推理算力是中模型级别的。**

**原因二：同算力预算下收敛更快**

Google Switch Transformer（2021）和后续多项研究反复验证：在相同计算预算下，MoE 模型的困惑度下降比同规模的 Dense 模型更快。花同样的钱训练，MoE 能学到更多。

**原因三：工程可行性已被验证**

在 GPT-4 之前，Google 的 GShard（2020）、Switch Transformer（2021）已经从工程上验证了稀疏 MoE 在大规模训练中是可行的——分布式训练、负载均衡、通信优化都有现成方案，OpenAI 不需要从零造轮子。

## 六、GPT-4 用 MoE 实现了什么？

简单说：**用可承受的成本，做出了一个能力远超 GPT-3.5 的模型，并为整个行业趟出了一条路。**

做个对比：

| 指标 | GPT-3.5 | GPT-4（第三方推测） |
|---|---|---|
| 架构 | Dense | MoE（16 专家） |
| 总参数 | ~175B | ~1.8T |
| 每 token 激活参数 | ~175B（全部） | ~280B（~16%） |
| MMLU 准确率 | ~70% | ~86.4% |
| Bar Exam 百分位 | ~10th | ~90th |

GPT-4 做对了三件事：

1. **知识广度的跃升**：多个专家各自存储不同类型的知识，总知识容量远超单一 Dense 模型
2. **推理成本的压缩**：激活参数仅为总参数的 ~16%，如果做成等规模的 Dense 模型，API 定价可能要翻数倍
3. **为行业探路**：GPT-4 的"疑似的成功"直接引爆了 2024 年开源 MoE 模型浪潮——Mistral、DeepSeek 等团队几乎都是沿着这条路杀进来的

## 七、MoE 不好做：三大工程难题

如果 MoE 这么好，为什么不是所有模型都用它？因为下面三个问题至今没有完美解决。

### 7.1 负载均衡：不能只有一个专家在干活

最经典的问题——训练过程中，路由器可能"偷懒"，把大部分 token 都推给某几个专家：

```
Expert 1  ████████████████████████  80%
Expert 2  ██████                    12%
Expert 3  ██                         5%
Expert 4  █                          3%
```

一旦出现这种情况，MoE 就退化了——大部分专家闲置，等于在做无用功，模型的有效容量大打折扣。

**解决方案演化：**

| 方案 | 做法 | 代表模型 |
|---|---|---|
| **Auxiliary Loss（辅助损失）** | 在训练 loss 里加一项，惩罚不均衡的专家使用 | Switch Transformer、GShard |
| **Bias Routing（偏置调整）** | 动态给每个专家加/减一个偏置项，热门专家降权、冷门专家提权 | DeepSeek-V3（auxiliary-loss-free） |
| **Capacity Factor（容量限制）** | 硬性限制每个专家最多处理多少 token，超出的直接丢弃 | Switch Transformer |

### 7.2 All-to-All 通信：MoE 最大成本来源

这是今天 MoE 最被低估的问题。

在分布式训练中，不同专家分布在不同 GPU 上。当 GPU 1 上的 token 需要路由到 GPU 8 上的专家时，就要跨卡通信：

```
Token Dispatch（发送 token）
    ↓
All-to-All 通信（跨 GPU 传输）
    ↓
Expert Compute（专家计算）
    ↓
All-to-All 通信（结果传回来）
    ↓
Token Gather（合并结果）
```

- 在大规模训练中，**超过 40% 的总时间消耗在 all-to-all 通信上**（Occult, ICML 2025）
- 通信开销随专家数量**平方级增长**
- 跨节点带宽（InfiniBand ~25-50 GB/s）远低于节点内带宽（NVLink ~900 GB/s）

换句话说：

> **很多时候，MoE 训练的瓶颈不是算力，而是网速。**

目前前沿的应对方案包括：Occult（ICML 2025）通过优化专家放置和协作剪枝实现 1.5-2× 加速；ScMoE 通过通信-计算重叠实现 30% 加速；NVIDIA NeMo 的 expert-parallel overlap 方案也有不错的效果——但这个问题仍然远未解决。

### 7.3 推理部署：从"复制粘贴"到"系统工程"

Dense 模型的部署逻辑很简单：

```
复制模型 → 部署上线 → 完成
```

MoE 模型的部署要复杂得多：

```
所有专家加载到显存（不能只加载激活的那几个）
    +
Router 计算 + 专家调度 + 结果合并
    +
负载均衡（多请求并发时的专家调度）
    +
KV Cache 管理（Attention 部分没有被稀疏化）
```

**核心矛盾**：虽然 MoE 的计算量小，但**显存占用跟总参数量成正比**。一个 671B 的 DeepSeek-V3，你必须把全部 671B 参数加载到显存里（或者至少准备好随时换入换出），不能"卸掉"不用的专家。

这就导致了一个有点反直觉的结果：

> **MoE 的推理成本优势主要体现在计算密集型场景（大批量 prefill），在访存密集型场景（小批量高并发生成）中优势大幅缩水。** Epoch AI 的分析显示，在快速短文本解码时，一个 8-way 稀疏 MoE 的等效成本约为其总参数量的 50%——不是 12.5%（1/8）。

很多团队训练能跑通，部署阶段被这三座大山卡住了。

## 八、Dense vs MoE：到底谁赢了？

看完上面的内容，你可能会觉得"MoE 显然比 Dense 好"。但实际情况要微妙得多。

### 8.1 一张表说清各自优劣

| 维度 | Dense | MoE |
|---|---|---|
| 同等训练预算下的效果 | 较小模型，上限较低 | **更大容量，通常更好** |
| 同等总参数下的推理速度 | 慢（全部参数参与） | **快**（只激活部分专家） |
| 显存占用 | 和参数量成正比 | **和总参数量成正比**（劣势！） |
| 训练稳定性 | **好**，不容易出现 loss spike | 较差，路由崩溃可能导致训练失败 |
| 工程复杂度 | **低**，部署简单 | 高，需要专家并行 + 通信优化 |
| 微调友好度 | **好**，全参数/ LoRA 都成熟 | 较差，容易过拟合，对 batch size 敏感 |
| 本地/边缘部署 | **好**，模型小、架构简单 | 差，显存需求大 |

### 8.2 当前行业共识

| 场景 | 更适合 | 原因 |
|---|---|---|
| 小模型（<10B） | Dense | MoE 的 overhead 超过收益 |
| 中等模型（10B-70B） | **都可以** | Dense 和 MoE 互有胜负 |
| 超大模型（>100B） | **MoE** | Dense 在这个体量推理成本太高 |
| 多模态模型 | **MoE** | 不同模态天然适合不同专家 |
| 本地部署 / 移动端 | **Dense** | MoE 显存太大，手机扛不住 |
| 长文本推理（大批量） | **MoE** | 计算密集，激活参数少的优势大 |
| 高并发短文本生成 | **Dense** | 访存瓶颈覆盖了 MoE 的计算优势 |

### 8.3 一句金句

> **Dense 赢在简单，MoE 赢在规模。没有谁取代谁，只有谁更适合什么场景。**

## 九、MoE 的演化全景：从 1991 到 2026

### 9.1 完整时间线

| 时间 | 里程碑 | 核心贡献 |
|---|---|---|
| **1991** | Jacobs, Jordan, Nowlan, Hinton 发表 *Adaptive Mixtures of Local Experts* | MoE 概念诞生：多专家子网络 + 门控网络，在语音识别上初试啼声 |
| **1992-1994** | Jordan & Jacobs 提出层级 MoE（HME）+ EM 训练 | 树形专家结构，EM 算法优化 |
| **2017** | Shazeer et al. (Google) 发表 *Outrageously Large Neural Networks: The Sparsely-Gated MoE Layer* | **关键转折**：首次将稀疏 MoE 嵌入深度 LSTM，top-k 路由实现 "参数量巨大但计算可控"，137B 参数验证 |
| **2020** | Google GShard | 首次在 Transformer 中大规模使用 MoE，600B 参数翻译模型 |
| **2021.01** | Google Switch Transformer | 简化路由为 top-1，推到 1.6T 参数，系统化验证稀疏 MoE 的可扩展性和稳定性 |
| **2023.03** | GPT-4 发布（MoE 架构据信） | 第一个"出圈"的生产级 MoE 大模型，让全行业看到商用可行性 |
| **2023.12** | Mistral AI 发布 Mixtral 8×7B | **首个开源高质量 MoE 模型**，46.7B 总参数 / ~12.9B 激活，性能逼近 GPT-3.5，Apache 2.0 |
| **2024.05** | DeepSeek-V2 | DeepSeekMoE：细粒度专家（更多更小的专家）+ 共享专家，236B 总参数 / 21B 激活 |
| **2024.12** | DeepSeek-V3 | 671B 总参数 / 37B 激活，256 个路由专家 + 1 个共享专家，训练成本仅 ~$5.6M，震动业界 |
| **2025.04** | Meta Llama 4 Maverick | 128 个路由专家，17B 激活，~400B 总参数，原生多模态早期融合 |
| **2025.04** | 阿里 Qwen3-235B-A22B | 235B 总参数 / 22B 激活，思考/非思考双模式统一，Apache 2.0 全开源 |
| **2025-2026** | 学术前沿爆发 | DAG-MoE（图结构聚合）、SDG-MoE（辩论式交互）、UniPool（全局共享池）、HELLoRA（热专家 LoRA）等 |

### 9.2 三次重大跃迁

| 阶段 | 核心特征 | 代表工作 |
|---|---|---|
| **理论期（1991-2016）** | 小众集成学习方向，浅层网络，dense 激活 | Jacobs & Jordan 系列 |
| **稀疏化验证期（2017-2022）** | top-k 稀疏路由 + 深度 Transformer，证明大规模可行 | Shazeer 2017、GShard、Switch Transformer |
| **生产爆发期（2023-现在）** | MoE 成为大模型标配，开源全面铺开，专家设计走向精细化 | GPT-4、Mixtral、DeepSeek-V3、Llama 4、Qwen3 |

## 十、现在 vs 以前的 MoE：到底变了什么？

这是全文最值得认真看的一章——2024-2026 年的 MoE 前沿，已经和 2017-2023 年的"经典 MoE"发生了本质变化。

### 10.1 专家设计：从"复制粘贴"到"精细化分工"

**经典 MoE**（Switch Transformer、Mixtral）：专家初始化为 FFN 的 N 个拷贝，靠训练自然分化。常出现同质化问题——训完发现几个专家几乎一模一样，白训了。

**现代 MoE**：
- **DeepSeek 的细粒度专家**：把大专家拆成更多更小的专家（V3 有 256 个路由专家），每个只处理更窄的知识域
- **共享专家 + 路由专家分离**（DeepSeek）：一部分专家"常驻"每次都激活，处理通用知识；路由专家按需调配
- **EvoMoE（AAAI 2026）**：从初始化阶段就通过渐进多样化策略让专家分化，解决同质化

### 10.2 路由机制：从固定 top-k 到动态感知

**经典 MoE**：固定 top-1 或 top-2，一个 token 永远激活固定数量的专家。

**现代 MoE**：
- **Top-P 动态路由**（DREAM, 2026）：根据路由置信度自适应决定激活几个——简单 token 可能只激活 1 个，复杂 token 激活多个
- **模态感知路由**（EvoMoE）：路由器能识别输入是文本还是图像，据此做出不同选择
- **层级路由**（Hi-MoE, ICML 2026）：把路由分解为"组间均衡 + 组内专精"两步，专家利用率大幅改善

### 10.3 专家聚合：从简单加权到结构化交互

**经典 MoE**：专家各算各的，最后加权平均——专家之间没有沟通。

**现代 MoE**：
- **DAG-MoE（ICML 2026）**：用可学习的有向无环图组织专家交互，专家不再是孤岛——"先 A 处理，再 B 加工"
- **SDG-MoE（2026.05）**：引入辩论机制——专家之间互相支持（support graph）和批判（critique graph），经过多轮交互再出最终答案，困惑度比最强 baseline 还低 19.8%

### 10.4 专家管理：从"每层独享"到"全局共享"

**经典 MoE**：每层有自己的专家集合，层间互不共享。层数越多 → 专家参数线性增长。

**现代 MoE**（UniPool, 2026.05）：
- 所有层共享同一个全局专家池，各层的路由器从池中挑选
- 实验结果：只用原方案 41.6%~66.7% 的专家参数量，就能达到甚至超过原效果
- **专家的参数量不需要随层数线性增长**——对超大模型部署是巨大的成本利好

### 10.5 微调适配：从"整体微调"到"精准打击"

**经典 MoE**：全参数微调或全量 LoRA，成本高且容易过拟合。

**现代 MoE**（HELLoRA, 2026.05）：
- 只在**最常被激活的热门专家**上挂 LoRA 模块
- 在 DeepSeekMoE 上只用 LoRA 23.2% 的可训参数就超过了全量 LoRA 的效果
- 在 OlMoE 上实现 1.9× 训练吞吐 + 9.2% 精度提升

### 10.6 六个维度一句话总结

| 维度 | 经典 MoE（2017-2023） | 现代 MoE（2024-2026） |
|---|---|---|
| 专家粒度 | 粗（8-16 个大专家） | 细（128-256 个小专家） |
| 路由策略 | 固定 top-1/2 | 自适应 top-P、模态感知、层级路由 |
| 专家组织 | 每层独立拥有 | 全局共享池、可分可合 |
| 专家交互 | 无语义沟通，加权平均 | 图结构交互、辩论、链式推理 |
| 负载均衡 | 辅助 loss 强行拉平 | 无辅助 loss 偏置调整、组间均衡 |
| 微调方式 | 全参数 / 全量 LoRA | 热专家 LoRA、持续学习专属专家 |
| 多模态 | 文本单模 | 原生多模态早期融合 + 模态感知路由 |

## 十一、写在最后

MoE 的故事是一个值得回味的叙事：

1991 年，它作为一个巧妙的"分而治之"思想在浅层网络里安静待了二十多年。2017 年，Google 把它塞进深度网络，证明稀疏化行得通。2021 年，Switch Transformer 证明它能 scale 到万亿参数。2023 年，GPT-4 让它站到了聚光灯下。

2026 年的今天，MoE 早已不是简单的"把 FFN 复制几份加个路由器"。专家怎么设计、路由怎么决策、专家之间怎么协作、怎么在保持能力的前提下压缩部署成本——每个环节都在被重新定义。

而对于开发者来说，最重要的变化可能是：**MoE 已经从闭源大厂的独门绝技，变成了开源社区人手一个的基础设施**——从 Mixtral 到 DeepSeek-V3，从 Llama 4 到 Qwen3，任何人现在都可以用上 MoE 模型，甚至在自己的场景里微调它。

---

**一个趋势判断：**

```
2023 年以前的核心问题是：
  "如何把模型做得更大？"

2026 年以后的核心问题正在变成：
  "如何让不同专家更好地协作？"

从单体智能走向群体智能——
这可能正是 MoE 下一阶段演化的方向。
```
