AI 写代码越来越快，一个 PR 动辄就有几百行改动。

审核时，我们可能看过了文件、跑过了测试，也觉得代码大致合理。

但合并之后，如果有人问起某个关键行为，未必能马上说清楚。

比如，一条请求重复执行会发生什么？老数据会不会受影响？失败之后又该怎么恢复？

最近看到一种有意思的做法，叫 **PR Quiz**。它根据这次改动出几道题，让审核者在看完代码后回答。答题时发现说不清楚，就再回到代码里找答案。

![](https://cdn.jsdelivr.net/gh/visiongem/BlogImages@master/flutter/2026/pr0.png)

## PR Quiz 是怎么做的？

在这段视频里，作者演示了自己做的原型。

流程很直接。创建 PR 时，AI 根据改动生成几道选择题，放进 PR 描述。审核者看完代码后勾选答案，自动化工作流再检查有没有漏答、答得对不对。

视频中的演示 PR 有七道题，涉及数据如何从 Room 流向界面、收藏记录怎样迁移，以及后台同步失败时会发生什么。感兴趣的话，可以看看原题。

演示 PR：https://github.com/PL-Coding-GmbH/PR-Quiz-Demo/pull/3

如果把这项检查设为合并的必需条件，答题未通过就可以阻止合并。视频作者演示的是检查失败和通过的过程，当时并没有设置强制阻止合并的规则。

![](https://cdn.jsdelivr.net/gh/visiongem/BlogImages@master/flutter/2026/pr1.png)

## 题目可以帮我们发现什么？

我看完最想试的是出题这一步。假设你正在审核一个订单退款的 PR，描述里写着「支持退款回调，增加幂等处理」。你看过了回调入口，也看到了更新订单状态的代码。准备批准时，可以先问自己一句：**如果支付平台把同一条成功回调发来两次，第二次会发生什么？**

如果你得回去找那段代码，这个问题就有用了。你可能会发现，订单状态确实只更新一次，但通知还是会发两遍。也可能发现，自己刚才读到的测试只覆盖了两次回调先后到达的情况。

## 从这次改动最容易看漏的地方出题

除了重复回调，还可以围绕这次退款改动问：

- 如果退款失败，用户能不能重新申请？系统根据什么状态做判断？
- 如果这次改动新增了退款状态字段，发布前创建的订单走到退款流程时会读到什么？

这些题都得结合具体的代码改动。比如这次根本没改数据库，就删掉关于新字段的问题。如果改的是回调处理，我会请审核者指出拦住重复处理的是哪段逻辑，以及对应测试覆盖了什么。这样遇到争议时，讨论能直接落到实现上。

## 先在一个 PR 上试试

提 PR 的时候，可以让 AI 根据代码改动起草几道题，顺带指出每道题涉及的代码或测试。提交者先核对一遍题意和预期行为，再把题目放进 PR 描述。审核者在审查评论里写下自己的判断。要是对不上，就沿着代码一起查。最后可能是实现有问题，也可能是题目把需求说错了。

PR 后续有新提交时，顺手检查题目是否还适用。比如第一次评审之后把去重逻辑从应用层移到了数据库，之前对并发回调的回答就值得重新看一遍。

AI 生成的题目和答案也需要提交者核对。题目有歧义、答案过时，或者只考实现细节，都可能让审核多一道流程，却没有帮助大家理解改动。

答对题也只是一次理解检查。正常的代码审查、测试和对风险的判断仍然要做。

![](https://cdn.jsdelivr.net/gh/visiongem/BlogImages@master/flutter/2026/pr2.png)

## 写在最后

我会先选一个涉及状态变化的 PR，试着写两三道题，看看它们能不能帮助审核者发现遗漏。

等团队试过几次，再决定哪些问题适合做成选择题，哪些留在审查评论里讨论，以及是否值得接入 CI。
