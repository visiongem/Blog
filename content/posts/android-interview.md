这篇文章整理了 14 道 Android 面试题，主要涉及 AI 辅助开发、团队协作、实时通信、Kotlin 协程、Flow、架构设计以及线上问题排查。

每道题尽量从实际开发场景出发，不只整理概念，还会分析技术原理、使用场景和容易被追问的细节。

部分答案提供了参考回答，但实际面试时还是要结合自己的项目经历。尤其是团队人数、项目职责、技术选型和性能优化成果，不要把示例当成自己的真实经历。

## 一、AI 辅助开发与团队协作

### 1. 除了开发需求和修复 Bug，你还会使用 AI 做什么？

**参考答案：**

AI 在开发中的用途不应该只局限于生成代码，还可以参与整个开发流程。

我主要会从以下几个方面使用 AI：

| 使用场景 | AI 可以辅助完成的工作 | 需要人工验证的内容 |
| --- | --- | --- |
| 阅读陌生项目 | 梳理模块结构、页面入口和调用链 | 是否找到真实调用方，有没有遗漏分支 |
| 测试设计 | 分析边界条件、生成测试用例 | 用例是否符合实际业务规则 |
| 代码审查 | 检查潜在 Bug、状态修改和异常处理 | 问题是否真实存在，修改是否引入新问题 |
| 技术调研 | 比较技术方案、整理官方文档 | 技术结论、版本和适用条件是否准确 |
| 性能分析 | 整理日志、分析 Trace 中的异常线索 | 是否有实际测量证据 |
| 文档整理 | 生成技术文档、流程图和变更说明 | 技术内容是否正确，逻辑是否完整 |

例如，接手一个陌生项目时，可以先让 AI 分析项目目录，寻找某个页面对应的 Activity、Fragment 或 Compose 页面，再继续追踪 ViewModel、Repository 和网络请求之间的调用关系。

遇到 Bug 时，也可以让 AI 根据异常日志和相关代码提出可能的原因，再通过断点、日志或测试用例验证。

不过，AI 给出的结论不能直接当成事实。尤其是涉及线程安全、协程取消、生命周期和业务状态时，必须结合代码实际执行过程判断。

**面试回答重点：**

不要只说自己使用过哪些 AI 工具，而要说明三个问题：

- 输入了什么信息？
- AI 帮助完成了什么工作？
- 最终如何验证结果？

真正有价值的不是 AI 生成了多少代码，而是它有没有帮助自己更快地理解问题、缩小排查范围和提高开发效率。

### 2. 把 Bug 地址交给 AI，它是怎么定位到具体页面并修复问题的？

首先要明确：Bug 管理系统的 URL 通常只是问题记录的入口，并不等于 App 内部的页面路由。

如果使用的是具备代码检索和工具调用能力的编程 Agent，一般会经历以下过程：

```text
读取 Bug 记录
    ↓
提取问题描述、复现步骤和附件
    ↓
分析项目代码，寻找页面入口
    ↓
追踪 ViewModel、Repository 和数据流
    ↓
分析可能的异常原因
    ↓
复现问题并验证假设
    ↓
修改代码
    ↓
运行测试并进行回归
```

**第一步：读取 Bug 信息**

Agent 首先需要通过已授权的连接器、API 或浏览器读取 Bug 记录。

通常会获取：

- Bug 标题和详细描述。
- 问题复现步骤。
- 设备型号和系统版本。
- 截图、日志和异常堆栈。
- 问题对应的 App 版本。

如果没有访问权限，仅仅提供一个 URL 并不能保证 AI 可以读取里面的内容。

**第二步：定位具体页面**

AI 会从问题描述中提取线索，例如：

- 页面标题。
- 按钮文案。
- 资源 ID。
- 接口地址。
- 日志标签。
- 页面路由。
- 异常堆栈。

然后通过代码搜索，寻找对应的 Activity、Fragment、Compose 页面或导航配置。

找到页面后，再继续追踪 ViewModel 和 Repository，分析页面数据从哪里来，又是如何更新的。

例如，Bug 描述是：

> 合约页面平仓成功后，仓位卡片仍然显示，没有及时消失。

AI 可以从“合约”“平仓”“仓位”等关键词开始搜索，找到仓位页面对应的代码，再检查平仓结果处理、列表数据更新和 Socket 推送逻辑。

**第三步：分析问题原因**

找到相关代码并不代表已经找到根因。

还需要结合实际执行过程验证，例如：

- 是否存在旧请求覆盖新数据？
- 是否有多个数据源同时更新页面？
- 是否存在并发修改？
- 页面销毁后是否仍然收到回调？
- 是否存在缓存数据没有及时更新？

如果有模拟器或测试设备，可以尝试复现问题，结合日志和 UI 层级进一步确认。

**第四步：修改并验证**

定位到问题后，Agent 可以提出修改方案、生成代码并运行测试。

但最终仍然需要人工审查修改内容，确认没有破坏原有业务逻辑。

**原理解析：**

AI Agent 并不是直接通过 Bug URL 就知道整个项目发生了什么。

它的工作方式更接近一个循环：

```text
模型分析当前信息
    ↓
选择合适的工具
    ↓
执行代码搜索或其他操作
    ↓
获取工具返回结果
    ↓
模型根据结果继续分析
```

模型负责分析和决策，工具负责真正访问代码、执行命令和获取运行结果。

**面试回答重点：**

要突出 AI 定位问题依赖的是问题描述、代码检索、调用链分析和实际运行证据，而不是简单地把一个 URL 丢给 AI 就能自动修复所有 Bug。

### 3. 你参与过最大的团队有多少人？团队成员之间是怎么分工的？

回答时建议区分项目组总人数和 Android 开发人数。

**参考回答：**

> 我参与过最大的项目组大约有 [人数] 人，其中 Android 开发 [人数] 人，其他成员包括产品、设计、后端、测试等角色。
>
> Android 侧主要按照业务模块进行分工，我负责 [模块 A] 和 [模块 B]，其他同事负责 [模块 C]。
>
> 公共基础组件由 [实际负责人或团队] 维护。涉及跨模块需求时，会提前确认接口定义、数据结构和职责边界，再进行开发联调。
>
> 遇到公共模块或接口变更时，会通过代码审查和联调确认影响范围，避免不同模块之间出现重复修改。

除了人数，最好再准备一个实际协作案例。

例如：

- 两个模块需要使用同一个公共接口，如何确定接口归属？
- 后端修改接口字段后，如何协调各模块？
- 两个开发人员同时修改同一业务模块，如何避免代码冲突？
- 项目进度出现依赖问题时，如何协调？

**答案解析：**

面试官问团队人数，通常不是单纯想知道团队规模，而是想了解你是否具备多人协作经验。

因此，回答时要重点说明自己负责什么、与谁协作，以及遇到跨模块问题时如何解决。

## 二、实时通信与数据一致性

![](https://cdn.jsdelivr.net/gh/visiongem/BlogImages@master/android/2026/android_i1.png)

### 4. WebSocket 和 MQTT 有什么区别？实际项目中应该如何选择？

首先要明确，WebSocket 和 MQTT 并不是完全对立的两种技术。

WebSocket 提供持久连接上的双向通信能力，而 MQTT 是一种基于发布订阅模型的消息协议。

MQTT 也可以运行在 WebSocket 之上。

**1. WebSocket**

WebSocket 是一种全双工通信协议，客户端和服务端建立连接后，双方都可以主动发送消息。

它的特点包括：

- 支持双向通信。
- 建立连接后可以持续传输数据。
- 适合实时消息、行情推送和在线状态更新。
- 消息格式和业务订阅机制通常由应用层自行定义。

**2. MQTT**

MQTT 是一种轻量级发布订阅消息协议，通常通过 Broker（消息代理）进行消息转发。

它提供了更完整的消息管理能力：

- Topic：通过主题组织消息。
- QoS：定义不同级别的消息交付保证。
- Session：支持会话状态管理。
- Retained Message：保留消息。
- Last Will：客户端异常断开时发布遗嘱消息。

**3. 两者对比**

| 对比维度 | WebSocket | MQTT |
| --- | --- | --- |
| 通信方式 | 全双工通信 | 发布订阅 |
| 消息组织 | 通常由业务自行定义 | 使用 Topic |
| 消息交付 | 由业务层设计 | 提供 QoS 机制 |
| 会话管理 | 需要业务层设计 | 提供会话机制 |
| 基础设施 | WebSocket 服务端或网关 | MQTT Broker |
| 常见场景 | Web/App 实时通信 | IoT、设备消息、实时消息系统 |

需要注意，MQTT 的 QoS 有三个级别：

- QoS 0：至多一次。
- QoS 1：至少一次。
- QoS 2：协议层恰好一次。

QoS 2 并不意味着整个业务一定只执行一次。比如支付、下单等操作，仍然需要业务幂等设计。

**4. 实际项目如何选择？**

不能简单地说 MQTT 比 WebSocket 更快，或者 WebSocket 比 MQTT 更实时。

应该结合项目需求判断。

如果项目已经有成熟的 WebSocket 网关，业务层也具备订阅、消息确认和数据恢复机制，那么继续使用 WebSocket 可能更合适。

如果项目需要管理大量设备、复杂 Topic、消息交付等级和会话恢复，那么可以考虑 MQTT。

**面试回答重点：**

> 我会结合项目的通信模型和服务端基础设施进行选择。如果现有 WebSocket 方案已经能够满足双向通信、订阅和数据恢复需求，就没有必要为了使用 MQTT 而增加一套基础设施。如果需要 MQTT 的发布订阅、QoS 和会话能力，就可以考虑采用 MQTT。

### 5. WebSocket 断线后如何重连？如何恢复数据并尽量避免消息丢失？

这道题比单纯询问如何重连更有实际价值。

因为连接恢复不代表数据已经恢复，真正需要解决的是连接状态、订阅状态和业务数据的一致性。

可以分为三个部分。

**1. 如何发现连接断开？**

常见方式包括：

- 监听 WebSocket 的连接关闭回调。
- 监听连接异常。
- 通过心跳检测连接状态。
- 设置心跳超时时间。

例如，客户端定期发送 Ping，服务端返回 Pong。

如果超过指定时间没有收到预期响应，就可以认为连接可能已经失效。

但需要注意，心跳正常只能说明连接具备响应能力，不能证明业务消息没有积压。

**2. 如何实现自动重连？**

可以设计一个统一的连接管理器，负责管理 WebSocket 的连接状态。

例如：

```text
DISCONNECTED
      ↓
CONNECTING
      ↓
CONNECTED
      ↓
连接异常
      ↓
RECONNECTING
      ↓
重新连接
      ↓
CONNECTED
```

重连时需要注意：

- 避免多个页面同时触发重连。
- 使用指数退避，避免频繁请求服务端。
- 增加随机抖动，减少大量客户端同时重连。
- 区分网络异常和鉴权失败。
- 网络恢复后合理触发重连。
- 账户切换时取消旧连接及旧任务。

**3. 如何恢复数据并尽量避免消息丢失？**

这是最重要的部分。

假设客户端正在接收仓位数据：

```text
服务端发送：
消息 101
消息 102
消息 103
```

客户端收到 101、102 后突然断网。

重新连接后，如果服务端直接发送最新消息 110，那么客户端就可能缺少 103～109 之间的更新。

因此，需要设计业务层的数据恢复机制。

常见方案是：

**第一步：记录消息序号**

客户端记录最后成功处理的消息序号，例如 102。

**第二步：重新连接并恢复订阅**

连接成功后，客户端将最后处理的序号告诉服务端。

**第三步：补发缺失消息**

如果服务端支持消息补发，就从 103 开始补发。

如果服务端不支持补发，则重新获取完整数据快照。

快照可以帮助恢复当前状态，但不能还原断线期间的每一条历史事件。如果业务需要保留逐笔成交、操作记录等事件，还需要服务端持久化事件，并设计补发和确认机制。

**第四步：处理重复消息和乱序消息**

客户端根据消息序号或业务版本判断：

- 重复消息：丢弃。
- 旧消息：丢弃。
- 缺失消息：触发补拉。
- 新消息：正常处理。

**第五步：同步快照和增量数据**

假设重新获取的快照版本为 V，那么客户端需要按照服务端约定的同步边界，缓存并处理 V 之后的增量消息。

如果快照和增量无法对齐，就重新同步。

需要注意，这种方案依赖服务端提供可靠的版本号、消息序号或同步边界，仅靠客户端接收时间无法保证数据一致性。

**面试回答重点：**

> 我会将连接恢复和数据恢复分开处理。连接层通过心跳、异常回调和退避重连恢复连接；业务层通过消息序号、去重、补发或重新获取快照恢复数据。重连成功后还需要确认订阅恢复和数据连续性，不能直接认为连接成功就代表数据已经最新。

## 三、Kotlin 协程与异常处理

![](https://cdn.jsdelivr.net/gh/visiongem/BlogImages@master/android/2026/android_i2.png)

### 6. 协程树中，子协程发生异常会影响父协程和其他子协程吗？

首先看普通 Job 的情况。

假设有以下协程结构：

```text
Parent
├── Child A
├── Child B
└── Child C
```

如果 Child A 发生未处理的异常：

1. Child A 进入失败状态。
2. 异常向父协程传播。
3. Parent 被取消。
4. Parent 取消其他子协程。
5. Child B 和 Child C 也会被取消。

也就是说，普通 Job 的子协程失败可能影响整个协程树。

**那么 SupervisorJob 呢？**

SupervisorJob 可以隔离直接子协程之间的失败。

例如：

```text
SupervisorJob
├── Child A
├── Child B
└── Child C
```

如果 Child A 失败，不会因为这次失败而取消 SupervisorJob，也不会自动取消 Child B 和 Child C。

但是，这里有一个容易被忽略的细节：

**SupervisorJob 只隔离对应父子关系中的失败传播，不代表所有后代协程都完全独立。**

例如：

```text
SupervisorJob
├── Parent A
│   ├── Child A1
│   └── Child A2
└── Parent B
```

如果 Child A1 失败，它仍然可能导致普通父协程 Parent A 失败，并取消 Child A2。

但是这个失败不会继续导致 SupervisorJob 取消 Parent B。

另外，还需要注意：

- 父协程取消时，仍然会向下取消子协程。
- 子协程主动取消自己，通常不会因此取消父协程。
- CancellationException 通常表示协程正常取消，不作为普通失败处理。
- 监督关系不会自动处理异常。

**再看 supervisorScope。**

```kotlin
suspend fun loadData() = supervisorScope {
    launch {
        loadUser()
    }

    launch {
        loadOrders()
    }
}
```

两个直接子协程之间的失败不会自动互相取消。

但隔离失败不等于处理了异常：如果 `launch` 中的异常没有被捕获，仍会交给协程异常处理机制，可能导致应用崩溃。实际代码应在子协程中处理预期异常，并保留取消行为。

但如果 `supervisorScope` 自身的代码块失败，例如代码块中执行了一个失败的 `await()`，作用域本身仍然会失败，并取消其子协程。

**面试回答重点：**

> 普通 Job 下，子协程未处理的异常会向父级传播，父级取消后会影响其他子协程。SupervisorJob 可以隔离直接子协程之间的失败，但父级取消仍然会向下传播。需要注意，SupervisorJob 只是改变异常传播规则，并不意味着异常已经被处理。

### 7. launch 中发生异常，为什么在外面使用 try-catch 捕获不到？

这是 Kotlin 协程中比较经典的一道题。

先看代码：

```kotlin
try {
    scope.launch {
        repository.refresh()
    }
} catch (e: Exception) {
    println("捕获异常")
}
```

假设 `repository.refresh()` 内部抛出 IOException。

上面的 try-catch 通常捕获不到这个异常。

原因是：`launch` 启动一个新的协程，协程体中的异常由协程的 Job 和异常传播机制处理，不会作为普通异常重新抛回 `launch()` 的调用位置。新协程通常仍与父协程存在父子关系。

**正确方式一：在 launch 内部处理异常。**

```kotlin
scope.launch {
    try {
        repository.refresh()
    } catch (e: CancellationException) {
        throw e
    } catch (e: IOException) {
        println("请求失败：${e.message}")
    }
}
```

这里需要特别注意 CancellationException。

它表示协程取消，通常应该继续向上传播，而不是当成普通业务异常吞掉。

**正确方式二：使用 coroutineScope，让异常向调用方传播。**

```kotlin
suspend fun refreshAll() {
    try {
        coroutineScope {
            launch {
                repository.refreshPositions()
            }

            launch {
                repository.refreshOrders()
            }
        }
    } catch (e: CancellationException) {
        throw e
    } catch (e: IOException) {
        println("刷新失败：${e.message}")
    }
}
```

为什么这里可以在外面捕获？

因为 `coroutineScope` 会等待内部子协程执行完成。

如果其中一个子协程失败，异常会导致作用域失败，并传播给调用方，因此外层 try-catch 可以捕获。

**那么 launch 和 async 有什么区别？**

| 对比 | launch | async |
| --- | --- | --- |
| 返回值 | Job | Deferred |
| 主要用途 | 启动不需要返回结果的任务 | 启动需要返回结果的任务 |
| 获取结果 | 不提供结果 | 使用 await() |
| 异常处理 | 通过协程异常传播机制处理 | await() 会重新抛出 Deferred 的失败异常 |

例如，在 `supervisorScope` 中处理 `async` 的失败：

```kotlin
suspend fun loadUserSafely() = supervisorScope {
    val deferred = async {
        repository.loadUser()
    }

    try {
        deferred.await()
    } catch (e: IOException) {
        println("加载失败")
        null
    }
}
```

这里的 await() 会将 Deferred 中的失败异常重新抛出。

但还有一个容易被忽略的地方：普通父子关系下，async 的失败也可能先取消父协程，并不意味着只有调用 await() 时才会产生影响。

另外，`Job.join()` 只负责等待任务结束，不会像 `Deferred.await()` 一样重新抛出目标任务的原始失败异常。

**面试回答重点：**

> launch 外层的 try-catch 只能捕获 launch 调用本身同步抛出的异常，不能捕获协程体中的异步失败。业务异常通常在协程内部处理；如果使用 coroutineScope，可以通过作用域失败将异常传播给调用方。async 则通过 await 获取结果并重新抛出失败异常。

## 四、Android 架构设计与 Flow

### 8. MVP、MVVM、MVI 有什么区别？为什么项目中选择 MVVM？

**1. MVP**

MVP 将界面和业务逻辑分开。

主要角色：

- Model：负责数据。
- View：负责界面展示。
- Presenter：负责业务逻辑和协调数据。

通常由 View 将用户操作交给 Presenter，Presenter 获取数据后，再通过 View 接口更新页面。

优点是职责比较明确。

缺点是 Presenter 容易变得庞大，而且需要注意 View 的生命周期和引用管理。

**2. MVVM**

MVVM 将页面状态和部分页面业务逻辑放到 ViewModel 中。

主要角色：

- Model：负责数据和业务数据来源。
- View：负责界面展示和用户交互。
- ViewModel：负责页面状态和页面操作。

典型数据流：

```text
用户操作
    ↓
View
    ↓
ViewModel
    ↓
Repository
    ↓
数据源
    ↓
Repository
    ↓
ViewModel
    ↓
State
    ↓
View 更新页面
```

ViewModel 不直接持有 Activity 或 View 的引用，从而降低界面生命周期对业务状态的影响。

**3. MVI**

MVI 更强调单向数据流和状态转换。

通常会有三个核心概念：

- Intent：用户输入或业务事件。
- Model：根据输入处理业务逻辑。
- View：根据 State 渲染界面。

典型流程：

```text
用户操作
    ↓
Intent
    ↓
业务处理
    ↓
State
    ↓
View 渲染
    ↓
用户再次操作
```

它强调状态更新的统一入口，以及状态变化过程的可追踪性。

**三种架构对比：**

| 对比 | MVP | MVVM | MVI |
| --- | --- | --- | --- |
| 核心角色 | Presenter | ViewModel | Intent、State |
| 数据更新 | Presenter 调用 View | View 观察状态 | State 驱动 View |
| 状态管理 | 由 Presenter 协调 | ViewModel 管理 | 强调统一状态转换 |
| 主要特点 | View 与业务逻辑分离 | 页面状态管理 | 单向数据流 |
| 主要成本 | 接口和引用管理 | 状态更新规则 | 状态建模与副作用管理 |

**为什么选择 MVVM？**

Android 项目中使用 MVVM，通常是因为它与 AndroidX ViewModel、Lifecycle、StateFlow 等组件结合比较自然。

例如：

- ViewModel 管理页面状态。
- Repository 负责数据获取和数据整合。
- View 负责展示状态和处理用户交互。
- StateFlow 负责向 UI 暴露状态。

对于大多数普通业务页面，这种结构已经足够清晰。

当页面状态比较复杂时，也可以在 MVVM 的基础上引入 MVI 风格的单向数据流。

需要注意，MVVM 并不要求使用 LiveData，也不要求双向数据绑定。使用 StateFlow 管理状态，同样可以采用 MVVM。

**面试回答重点：**

> 我选择 MVVM 主要是考虑项目复杂度、团队协作和 Android 官方组件的支持。ViewModel 管理页面状态，Repository 负责数据，View 负责渲染。对于输入来源较多、状态转换复杂的页面，可以引入 MVI 风格的单向数据流，但没有必要为了使用某个架构名称而增加复杂度。

### 9. LiveData 和 Flow 有什么区别？为什么现在更倾向于使用 Flow？它和 MVI 有什么关系？

这道题实际上包含两个问题：

1. LiveData 和 Flow 的技术区别。
2. Flow 与 MVI 的关系。

首先要明确，LiveData 和 Flow 都可以用于观察数据变化，但它们的设计目标和适用场景有所不同。

**1. LiveData**

LiveData 是 Android Jetpack 提供的生命周期感知型可观察数据持有者。

特点：

- 与 Android Lifecycle 集成。
- 可以感知 Activity 和 Fragment 的生命周期。
- 观察者处于活跃状态时才会收到更新。
- 支持通过 MediatorLiveData 等方式组合数据。

它在传统 Android MVVM 项目中使用比较广泛。

**2. Flow**

Flow 是 Kotlin Coroutines 提供的异步数据流。

特点：

- 可以表示连续产生的数据。
- 支持 map、filter、combine 等操作符。
- 支持协程取消。
- 可以通过 flowOn 调整上游执行上下文。
- 可以通过 StateFlow 和 SharedFlow 实现不同的数据共享方式。

Flow 不依赖 Android，因此 Repository、Domain 和 ViewModel 等层都可以使用。

**对比：**

| 对比 | LiveData | Flow |
| --- | --- | --- |
| 所属 | Android Jetpack | Kotlin Coroutines |
| 生命周期 | 内置生命周期感知 | 需要结合 Lifecycle API |
| 数据组合 | 支持 MediatorLiveData 等方式 | 提供丰富的 Flow 操作符 |
| 执行上下文 | 观察回调在主线程执行 | 可以通过 flowOn 等控制上游上下文 |
| 使用范围 | Android 平台 | 可用于更广泛的 Kotlin 环境 |
| 取消机制 | 依赖观察生命周期 | 与协程取消机制结合 |

这里需要注意，Flow 本身并不会自动切换到后台线程，耗时操作仍然需要合理指定执行上下文。

另外，Android UI 收集 Flow 时，通常应该使用 `repeatOnLifecycle`，或者在 Compose 中使用 `collectAsStateWithLifecycle()`。

**3. Flow 和 MVI 有什么关系？**

Flow 和 MVI 不是同一个层面的技术。

Flow 是数据流工具，MVI 是一种架构组织方式。

例如，一个仓位页面可能同时接收：

- HTTP 刷新结果。
- WebSocket 实时推送。
- 用户筛选条件。
- 用户平仓操作。

如果使用简单的 MVVM，可以让 ViewModel 通过多个 Flow 观察数据，再更新页面状态。

如果使用 MVI 风格，可以进一步统一输入事件和状态转换：

```text
刷新操作
    ↓
RefreshIntent

实时推送
    ↓
PositionUpdateIntent

筛选操作
    ↓
FilterIntent

        ↓
统一处理
        ↓
State 更新
        ↓
UI 渲染
```

这样可以更清晰地管理复杂页面的状态变化。

但并不是使用 Flow 就必须采用 MVI，LiveData 也可以承载 MVI 中的状态。

**面试回答重点：**

> LiveData 与 Android 生命周期结合比较方便，Flow 则更适合融入 Kotlin 协程体系，具备丰富的数据组合和取消能力。Flow 解决的是数据流处理问题，MVI 解决的是状态和输入如何组织的问题，两者不能混为一谈。

### 10. Flow 用过哪些操作符？分别有什么作用？

这道题建议按照用途回答，而不是单纯背操作符名称。

**1. 数据转换与过滤**

| 操作符 | 作用 |
| --- | --- |
| map | 转换数据 |
| filter | 过滤不符合条件的数据 |
| distinctUntilChanged | 忽略连续相同的数据 |
| debounce | 防抖，在一段时间没有新数据后才发射 |

例如搜索框输入：

```kotlin
searchFlow
    .debounce(300)
    .distinctUntilChanged()
    .filter { it.isNotBlank() }
    .collect {
        search(it)
    }
```

用户停止输入 300 毫秒后才执行搜索。这里使用普通 `collect`，如果当前搜索还没完成，后续输入的处理可能需要等待；需要取消旧搜索时，可以参考下面的 `flatMapLatest` 示例。

**2. 数据组合**

| 操作符 | 作用 |
| --- | --- |
| combine | 组合多个 Flow 的最新值 |
| zip | 按顺序配对多个 Flow 的数据 |
| merge | 将多个 Flow 的数据合并到一个 Flow |

具体区别后面会单独说明。

**3. 并发处理**

| 操作符 | 作用 |
| --- | --- |
| flatMapLatest | 新数据到来时取消之前的内部 Flow |
| collectLatest | 新数据到来时取消之前的处理逻辑 |
| buffer | 缓冲数据，减少生产者和消费者之间的相互等待 |
| conflate | 消费较慢时跳过中间值，优先处理最新值 |

例如搜索场景：

```kotlin
searchFlow
    .debounce(300)
    .distinctUntilChanged()
    .flatMapLatest { keyword ->
        repository.search(keyword)
    }
    .collect { result ->
        updateUI(result)
    }
```

如果用户连续输入多个关键词，新的搜索会取消之前的搜索流。

这里有一个细节：`flatMapLatest` 取消的是旧 Flow 对应的协程，不代表已经发到服务端的请求一定被撤销，也不代表服务端业务操作已经回滚。

**4. 异常处理与线程切换**

| 操作符 | 作用 |
| --- | --- |
| catch | 捕获上游异常 |
| retryWhen | 根据条件决定是否重试 |
| flowOn | 调整上游 Flow 的执行上下文 |
| onStart | 在数据发射前执行操作 |
| onCompletion | 在 Flow 完成或取消时执行操作 |

例如：

```kotlin
flow {
    emit(repository.loadData())
}
    .flowOn(Dispatchers.IO)
    .catch { e ->
        emit(emptyList())
    }
    .collect { data ->
        updateUI(data)
    }
```

这里使用 IO 调度器执行上游操作，catch 处理上游异常。

需要注意：

- catch 只处理它上游的异常。
- flowOn 只影响它之前的上游操作。
- catch 不会自动捕获后面 collect 中的异常。
- 不能随意吞掉 CancellationException。

**5. 数据共享**

| 操作符 | 作用 |
| --- | --- |
| stateIn | 将 Flow 转换成 StateFlow |
| shareIn | 将 Flow 转换成 SharedFlow |

StateFlow 适合表示当前状态，始终持有一个最新值。

SharedFlow 适合向多个订阅者共享事件或数据流，可以配置重放和缓冲策略。

**面试回答重点：**

> 我主要使用 map、filter、debounce、distinctUntilChanged 处理数据转换和过滤，使用 combine 组合多个数据源，使用 flatMapLatest 处理搜索等需要取消旧任务的场景，使用 catch 和 retryWhen 处理异常，使用 stateIn 和 shareIn 共享数据。

### 11. 多个 Flow 如何合并？combine、zip、merge 有什么区别？

这是 Flow 中很容易混淆的三个操作符。

它们都能处理多个 Flow，但数据合并规则完全不同。

**1. combine：组合最新值**

combine 会等待所有 Flow 至少发射一次数据，然后使用各自最新的数据进行组合。

例如：

```kotlin
val userFlow = flowOf("用户A", "用户B")
val ageFlow = flowOf(20, 30)

combine(userFlow, ageFlow) { user, age ->
    "$user：$age"
}
```

需要注意，Flow 的实际执行时序会影响最终发射结果。combine 不保证保留每个上游的所有中间值。

适合多个数据源共同决定页面状态的场景。

例如：

- 仓位列表。
- 实时行情。
- 用户筛选条件。

三者组合后生成最终页面数据。

**2. zip：按顺序配对**

zip 会按照元素出现的顺序进行一一配对。

例如：

```text
Flow A：A1、A2、A3
Flow B：B1、B2、B3
```

结果：

```text
(A1, B1)
(A2, B2)
(A3, B3)
```

如果其中一个 Flow 提前结束，zip 就无法继续配对，最终会结束。

适合两个数据流之间存在明确顺序对应关系的场景。

**3. merge：合并数据流**

merge 不会把多个 Flow 的数据组合成一个对象，而是将它们发射的数据汇入同一个 Flow。

例如：

```text
Flow A：A1、A2
Flow B：B1、B2
```

合并后可能得到：

```text
A1
B1
A2
B2
```

具体交错顺序取决于实际执行时序，不保证某个固定顺序。

适合多个来源产生相同类型事件，需要统一处理的场景。

**三者对比：**

| 操作符 | 核心规则 | 常见场景 |
| --- | --- | --- |
| combine | 组合各来源最新值 | 多个数据源生成页面状态 |
| zip | 按位置一一配对 | 两个需要对应的数据流 |
| merge | 多个数据流汇入一个流 | 多个来源产生统一事件 |

**实际项目示例：**

假设仓位页面需要组合仓位数据、行情数据和筛选条件：

```kotlin
val rows: Flow<List<PositionRow>> = combine(
    repository.positions,
    repository.prices,
    selectedFilter
) { positions, prices, filter ->
    buildRows(positions, prices, filter)
}.flowOn(Dispatchers.Default)
```

各来源都至少发射过一次后，收到上游更新时会使用各来源的最新值重新计算页面列表。快速更新时，不保证每个中间值都触发一次计算。

这里还要注意，combine 并不是事务快照。如果多个来源需要严格对应同一个业务版本，就应该在数据层增加版本校验或统一快照机制。

**面试回答重点：**

> combine 适合组合多个来源的最新状态，zip 适合按顺序配对，merge 适合把多个同类数据流合并到一起。具体选择取决于数据之间是否存在对应关系，以及是否需要保留每次数据变化。

### 13. 项目中为什么使用 EventBus？它是不是已经过时了？

EventBus 是一种基于发布订阅模式的事件通信框架。

它允许事件发送者和事件接收者之间不直接持有引用，从而降低模块之间的直接依赖。

例如：

```text
模块 A 发送事件
       ↓
    EventBus
       ↓
模块 B 接收事件
```

模块 A 不需要知道模块 B 的具体实现。

**1. EventBus 的常见使用场景**

例如：

- 登录成功后通知其他模块更新用户状态。
- 某个操作完成后通知相关页面刷新。
- 不同模块之间传递简单的业务通知。
- 旧项目中用于页面间通信。

EventBus 提供了不同的线程模式，可以根据实际需求决定订阅方法在哪个线程执行。

**2. EventBus 有什么问题？**

虽然 EventBus 可以降低直接依赖，但也会引入一些隐式依赖。

主要问题包括：

- 事件发送者和接收者之间的关系不够直观。
- 需要全局搜索才能知道某个事件有哪些订阅者。
- 容易出现重复订阅或忘记注销。
- 多个订阅者同时修改业务状态，可能导致状态不一致。
- 事件本身无法天然表示当前业务状态。

例如，用户进入一个页面时，如果之前的登录成功事件已经发送完毕，那么新页面不一定能够收到这个事件。

因为 EventBus 默认主要用于事件通知，而不是保存当前状态。

**3. EventBus 是否已经过时？**

不能简单地说 EventBus 完全不能使用。

如果旧项目已经大量使用 EventBus，贸然全部替换可能带来很大的改造成本。

但对于新业务，更推荐明确数据和状态的归属。

例如：

```text
Repository
    ↓
ViewModel
    ↓
StateFlow
    ↓
UI
```

Repository 管理业务数据，ViewModel 管理页面状态，UI 观察状态变化。

对于一次性的事件，可以根据场景使用 SharedFlow、Channel 或明确的回调机制。

使用 SharedFlow 时，要结合订阅时机、重放和缓冲配置判断事件能否送达。例如，没有订阅者且 `replay = 0` 时，发出的事件不会留给之后的订阅者。对于不能丢失的结果，应考虑将其建模为可恢复的状态，并设计消费确认机制。

**4. SharedFlow 能完全替代 EventBus 吗？**

不能简单地认为两者可以直接等价替换。

SharedFlow 是 Kotlin 协程中的热流，可以向多个订阅者共享数据。

它可以配置：

- replay：新订阅者是否重放历史数据。
- extraBufferCapacity：额外缓冲容量。
- onBufferOverflow：缓冲区溢出策略。

但是，SharedFlow 本身并不会自动解决事件归属、模块依赖和生命周期管理问题。

如果只是把全局 EventBus 替换成全局 `MutableSharedFlow<Any>`，原来的隐式依赖依然存在。

**面试回答重点：**

> EventBus 主要用于模块之间的事件通知，优点是降低直接依赖，但缺点是事件关系不够直观，订阅生命周期和状态管理也需要额外维护。对于新业务，我更倾向于通过 Repository 和 ViewModel 明确状态归属，使用 StateFlow 管理页面状态，必要时再使用 SharedFlow 处理事件。

### 14. Release 包安装后打开，导致手机严重卡顿甚至无响应，应该如何排查？

首先需要明确一个问题：

**是 App 自己卡死，还是整个手机都卡死？**

两者的排查方向并不完全相同。

#### 第一步：确认问题范围

先观察：

- 只有当前 App 无响应，还是其他应用也无法操作？
- 通知栏、桌面和系统界面是否正常？
- ADB 是否还能正常连接？
- 问题发生在冷启动还是打开某个页面之后？
- 是否只在某个机型或 Android 版本出现？

如果只有当前 App 卡死，优先检查主线程、锁等待、Binder 调用和启动任务。

如果整个系统都明显卡顿，就需要进一步检查 CPU、内存、磁盘 I/O 和系统服务负载。

不能一开始就认定是主线程死循环。

#### 第二步：采集日志和系统信息

如果可以提前连接测试设备，建议在复现前开启日志采集。

```bash
# 持续采集日志
adb logcat -b all -v threadtime > release-startup.log
```

在另一个终端可以根据需要执行：

```bash
# 查看 CPU 使用情况
adb shell dumpsys cpuinfo

# 查看应用内存情况
adb shell dumpsys meminfo com.example.app

# 生成系统 Bugreport
adb bugreport ./release-freeze.zip
```

其中 `com.example.app` 需要替换为实际包名。

需要注意，如果设备已经完全无响应，ADB 命令也可能无法及时执行。因此，最好提前配置日志采集。

#### 第三步：使用 Perfetto 分析线程和 CPU

如果问题能够稳定复现，可以使用 Perfetto 录制系统 Trace。

重点观察：

- 主线程是否长时间占用 CPU。
- 是否存在大量线程同时运行。
- 是否发生锁竞争。
- 是否有 Binder 调用阻塞。
- 是否存在频繁的线程创建和销毁。
- 是否存在大量 I/O 操作。

例如：

如果主线程长时间处于 Runnable 状态，却得不到 CPU 调度，可能是系统负载过高。

如果主线程一直在执行大量计算，则需要检查具体的计算逻辑。

如果主线程处于锁等待状态，则需要继续寻找锁的持有者。

这几种情况的根因完全不同。

#### 第四步：重点排查以下问题

| 问题类型 | 可能原因 | 排查方向 |
| --- | --- | --- |
| 主线程耗时 | 大量计算、JSON 解析、复杂布局 | 主线程堆栈和 Trace |
| 死锁 | 多个线程互相等待锁 | 线程堆栈和锁持有情况 |
| Binder 阻塞 | 同步调用系统服务或其他进程 | Binder 调用链 |
| CPU 过高 | 死循环、忙轮询、频繁重试 | CPU 使用率和线程调度 |
| 内存异常 | 大对象分配、缓存过大、内存泄漏 | dumpsys meminfo 和 GC |
| 线程过多 | 无限制创建线程、任务积压 | 线程数量和线程池状态 |
| I/O 阻塞 | 大量日志写入、数据库操作 | I/O Trace 和文件访问 |

还要注意，ANR 堆栈中出现 `nativePollOnce` 并不代表 Looper 本身一定有问题。

需要结合主线程完整状态、系统负载和 ANR 原因进一步分析。

#### 第五步：为什么 Debug 正常，Release 才出现问题？

这是一个非常重要的排查方向。

Debug 和 Release 通常存在以下差异：

**1. R8 混淆与代码优化**

检查是否存在：

- 反射调用依赖的类或方法被裁剪。
- 序列化规则不正确。
- JNI 调用依赖的类名发生变化。
- 第三方 SDK 缺少必要的保留规则。

**2. 初始化逻辑不同**

某些项目只在 Release 中启用特定初始化逻辑，例如：

- 日志上报。
- 数据统计。
- 推送服务。
- 安全检测。
- 第三方 SDK 初始化。

需要检查这些逻辑是否引入了阻塞或资源竞争。

**3. 环境配置不同**

检查：

- API 地址是否一致。
- Release 是否连接了不同的服务端。
- 是否存在不同的初始化参数。
- 是否有不同的业务数据量。
- 是否存在不同的重试策略。

**4. 多线程和时序问题**

Release 优化后，执行时序可能发生变化，某些原本不容易出现的竞态问题可能被暴露出来。

因此不能只盯着混淆，也要检查线程安全和初始化顺序。

可以通过受控构建一次改变一个因素，逐步缩小问题范围。

如果涉及混淆堆栈，需要使用对应版本的 `mapping.txt` 进行还原。

#### 第六步：修复后如何验证？

不能只验证 App 能正常打开。

还需要检查：

- 冷启动是否正常。
- 覆盖安装是否正常。
- 首次初始化是否正常。
- 数据迁移是否正常。
- 弱网情况下是否正常。
- 不同机型和系统版本是否正常。
- 是否引入新的 CPU 或内存问题。

对于严重影响线上用户的问题，还需要结合发布流程评估暂停灰度、关闭问题功能或回滚版本。

**面试回答重点：**

> 我会先确认是应用无响应还是整个系统出现资源问题，再通过 Logcat、Bugreport 和 Perfetto 获取证据。重点检查主线程、线程调度、锁等待、Binder、CPU、内存和 I/O。如果只有 Release 出现，再对比 R8、初始化逻辑、环境配置和线程时序，逐步缩小范围。不会仅凭 Release 卡死就认定是混淆问题。

## 总结

这 14 道题覆盖了 Android 开发中几个比较重要的方向：

| 技术方向 | 对应题目 | 核心考查点 |
| --- | --- | --- |
| AI 辅助开发 | 第 1～2 题 | 工具使用、代码分析、问题定位 |
| 团队协作 | 第 3 题 | 职责划分、沟通协作 |
| 实时通信 | 第 4～5 题 | WebSocket、MQTT、断线恢复 |
| Kotlin 协程 | 第 6～7 题 | Job、SupervisorJob、异常传播 |
| 架构设计 | 第 8～9 题 | MVP、MVVM、MVI、LiveData、Flow |
| Flow | 第 10～11 题 | 操作符、数据组合 |
| 项目经验 | 第 12～13 题 | 项目难点、EventBus、状态管理 |
| 性能排查 | 第 14 题 | ANR、线程、CPU、内存、Release |

准备 Android 面试时，我觉得有三个方面尤其值得重视：

**第一，不能只记概念。**

例如知道 SupervisorJob 可以隔离子协程异常还不够，还要理解它的隔离边界，以及父协程取消时会发生什么。

**第二，要能结合项目解释技术选型。**

例如为什么选择 WebSocket、为什么使用 MVVM、为什么引入 Flow。回答时不仅要说明技术优点，还要知道它解决了什么问题，以及带来了什么成本。

**第三，要具备实际问题排查能力。**

无论是数据不一致、协程异常，还是 Release 包卡死，都应该能够从现象出发，提出假设，寻找证据，再验证根因。

技术面试最终考查的不只是记住多少知识点，更重要的是能不能把技术原理和实际开发中的问题联系起来。
