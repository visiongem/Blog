前面四篇，把「CLAUDE.md 写什么、删什么、放哪里」拆完了。这篇收尾，聊最后一个问题：**这些规则怎么长期维护？**

项目会变，Agent 会变，团队会变，我们使用 Agent 的方式也会变。规则不能写完就放着，得跟着项目一起进化，而不是慢慢腐烂。

![](https://cdn.jsdelivr.net/gh/visiongem/BlogImages@master/ai/2026/claude4.png)

## 一、规则会过期，所以要有生命周期

规则也会产生债务：项目早期定下「不允许使用 LegacyNetwork」，当时很有用；半年后项目迁移完成，LegacyNetwork 删光了，这条规则却还留着——Agent 看到还得先判断「这是不是还适用于当前项目」，这就成了噪音。

规则的价值不是「存在」，而是「当前仍然有效」。所以它应该有一套生命周期：

```text
发现问题 → 形成规则 → 验证 → 使用 → 产生反馈 → 定期健检 → 保留 / 修改 / 删除 → 继续进化
```

而不是「发现问题 → 写进 CLAUDE.md → 永远存在」。

## 二、好规则来自真实反馈，不是提前堆

不要为了「看起来专业」提前写一堆「不允许这样、必须那样」——它们到底解决过什么问题？可能一个都没有。

真正值得沉淀的规则来自真实事件：

- Agent 改了 `generated/`，覆盖了生成代码 → 记录「不要直接修改 generated 文件」
- Agent 改了 API，Mock 没同步，测试挂 → 记录「改 API 后必更新 Mock」
- Agent 改 Schema 没写 Migration，升级失败 → 记录「改 Schema 必写 Migration」

但也不是每次错误都要加规则。一次把变量名写错，不是系统性问题，观察就好。判断标准：

```text
一次错误 → 观察
重复错误 → 分析原因
系统性错误 → 沉淀规则
```

规则不是错误日志，而是从重复的系统性错误里提炼出的解决方案。

## 三、一份规则，多个 Agent

Claude Code、Codex、Cursor、Gemini CLI 各有各的规则入口（CLAUDE.md、AGENTS.md、Cursor Rules……）。如果每份都单独维护，很快就会分叉：Claude 里写「UI 禁止直接访问 Repository」，Cursor 里写「可以」，同一份代码就分裂了。

关键要区分：

> 规则入口 ≠ 规则源。

入口可以不同，但最好共享同一份核心规则。做法是建一个统一目录 `.agent/rules/` 当规则源，再让 CLAUDE.md、AGENTS.md 用软链接指向它——改一次，所有 Agent 同步，不用手动复制四份。

但别把所有东西都做成软链接。统一的是项目规则、架构规则、安全原则这类核心内容；工具专属能力（Hooks、Skills、.mdc）保留差异，因为不同 Agent 的能力本来就不一样。

这一节是整个系列从「CLAUDE.md」走向「Agent 工程体系」的关键，核心可以收成一句话：

```text
不是维护很多份规则
        ↓
而是维护一份规则源
        ↓
不同 Agent 做适配
        ↓
规则持续反馈和进化
```

## 四、给规则留来源、留删除条件，定期健检

每条重要规则，都应该知道自己为什么存在：

```md
- UI 层禁止直接访问 Repository。
  原因：过去直接访问导致业务逻辑散落在多个页面。
```

也要想清楚什么时候删，而不只是什么时候加：

```md
- 禁止直接修改 generated 文件。
  删除条件：生成流程完全自动化，仓库不再有人工维护的 generated。
```

然后定期健检（每月一次，或架构、技术栈大升级时）：有没有过期规则、重复规则、冲突规则？有没有新的高频错误值得沉淀？再配合一个反馈闭环——Agent 出错 → 人工修正 → 判断是否重复 → 确认是系统性问题就沉淀成规则，让 Agent 下次避免。这才是真正的 Agent 工程化。

## 五、少而重要

规则越多不等于越聪明。堆得越多，上下文越大，相关性越低，冲突越多，Agent 判断成本越高，规则反而失去价值。

规则的价值大概是一个公式：

```text
规则价值 ≈ 错误成本 × 发生概率 × AI 难以自行推断的程度
```

「变量用 camelCase」错误成本低、AI 自己就知道，价值很低；「金额统一按分存储」「支付状态只能由服务端确认」这种高错误成本、高隐性、长期有效的，才值得写。

写规则时别问「还能不能再加一条？」，而是问「**这条规则值得占用 AI 的注意力吗？**」这是整套规则治理里最核心的一句。

## 六、整套架构

把五篇串起来，理想形态是这样的：

```text
Agent 工作体系
   ├─ 长期项目规则（CLAUDE.md / Rules）：应该知道什么
   ├─ 任务流程（Skills）：应该怎么做
   └─ 强制执行（Hook / CI）：必须做到什么
            ↓
        统一规则源（.agent/）
            ↓
  Claude / Codex / Cursor 各自适配
            ↓
持续反馈 → 定期健检 → 保留 / 修改 / 删除 → 进化
```

构建的不是一个 CLAUDE.md，而是一套 Agent Configuration System。

## 写在最后

写到这，系列就结束了。

最开始只是想解决「CLAUDE.md 怎么写」，拆到最后发现根本问题是：**AI 开始参与软件开发后，怎么把人类的工程经验，转化成 AI 能稳定执行的工作协议。**

整套思路，其实可以浓缩成两个问题：

```text
一条规则，值得占用 AI 的注意力吗？
一套 Agent 体系，值得团队长期维护吗？
```

第一个问题决定「写什么」，第二个问题决定「怎么组织」。不再是一份 CLAUDE.md，而是一套 Agent 工程体系。

规则能被记录、被共享、被执行、被验证、被反馈、被更新，AI 才真正从一个会写代码的聊天机器人，变成团队工程体系里的长期协作者。这也是这个系列最后想留下的东西。
