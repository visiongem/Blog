上一篇聊了一个核心观点：

> CLAUDE.md 不是项目百科全书，而是 AI 工作时必须知道的项目规则。

但问题来了：

如果不能什么都写进去，那应该写什么？

很多人在整理 CLAUDE.md 时，会陷入两个极端：

第一种：

> 什么都不写。

觉得 AI 很聪明，自己探索项目就好了。

结果：

- AI 不知道业务约定；
- 不知道团队习惯；
- 经常重复犯错。

第二种：

> 什么都写。

把：

- 项目结构；
- 技术栈；
- 每个模块职责；
- 所有开发规范；
- 历史背景；

全部塞进去。

结果：

CLAUDE.md 变成了一份项目 Wiki。

真正好的 CLAUDE.md，需要找到中间点：

> **只记录 AI 很难自行确定，但又会影响工作结果的信息。**

![](https://cdn.jsdelivr.net/gh/visiongem/BlogImages@master/ai/2026/claude1.png)

---

## 一、先建立一个判断模型

以后看到 CLAUDE.md 中的一条内容，可以先问三个问题。

这里统一把各种 AI Coding Agent 简写为 Agent（Claude Code、Codex 等），后面不再反复带全名。

### 问题 1：Agent 能否通过正常探索项目得到这个信息？

如果可以，那么通常没有必要写。

例如：

```text
项目使用 Kotlin
````

AI 可以直接查看：

```text
build.gradle.kts
```

知道项目语言。

所以：

```text
不一定需要写。
```

---

### 问题 2：若Agent不知道这件事，会不会造成实际错误？

如果不会，那么优先级较低。

例如：

```text
项目作者喜欢把工具类放在 utils 包。
```

AI 不知道，可能也不会影响结果。

但是！

```text
所有金额统一使用分作为存储单位。
```

如果 Agent 不知道：

可能直接造成业务错误。

所以：

```text
值得写。
```

---

### 问题 3：这件事情是否长期有效？

CLAUDE.md 最大的问题就是：

今天正确，半年后错误。

例如：

```text
当前项目使用 Retrofit 2.9。
```

可能几个月后升级。

这种信息：

* 容易过期；
* 需要维护；
* 价值有限。

不适合作为长期规则。

---

所以，一条高价值规则通常满足：

```
无法轻易发现
+
错误成本较高
+
长期稳定
```

---

## 二、第一类：项目事实

很多人第一次整理 CLAUDE.md 时，最容易犯的错误，就是把“项目介绍”当成“项目规则”。

所以第一类，我们先聊最容易被误写进去的内容：

项目事实。

原因：

这一篇的核心就是区分：

Facts 和 Rules

提前点出来会更强。

很多 CLAUDE.md 开头都会出现：

```md
# Project Overview

这是一个 Android 项目。

使用 Kotlin 开发。

采用 MVVM 架构。

包含 app、data、domain 模块。

使用 Retrofit 进行网络请求。

使用 Room 保存数据。
```

这些内容有没有价值？

有。

但是：

**不一定要放在 CLAUDE.md。**

---

### 为什么？

因为它们属于：

> 项目事实（Project Facts）

项目事实通常存在于：

* Gradle 配置；
* 源代码；
* 文件结构；
* README；
* 项目文档。

AI 可以主动获取。

例如 Android 项目：

```
app/
feature_login/
feature_home/
core_network/
```

AI 看目录就知道模块关系。

再比如：

```kotlin
implementation("com.squareup.retrofit2:retrofit")
```

AI 看依赖就知道用了 Retrofit。

所以这里需要建立一个重要认知：

> **项目事实 ≠ 项目规则。**

项目事实描述：

> 这个项目现在是什么样。

项目规则描述：

> AI 在这个项目里应该怎么工作。

CLAUDE.md 更应该关注后者。

这个概念后面几篇还会反复用到。

---

## 那项目事实完全不能写吗？

也不是。

有些项目事实虽然能找到，但是：

### 1. 查找成本很高

例如：

> 这个项目有一个 payment-core 模块，所有支付逻辑必须经过这里。

代码里可能存在：

```
payment-core/
```

但是 AI 不一定知道它的重要性。

这种可以写。

---

### 2. 背后有特殊含义

例如：

```
legacy/
```

普通理解：

> 老代码。

但是团队知道：

> 这里是已经稳定运行多年的核心交易逻辑，不允许随意重构。

这个信息通过代码名字无法表达。

应该写！

---

所以判断标准不是：

> AI 能不能看到。

而是：

> AI 能不能理解它的重要性。

---

## 三、第二类：隐性业务规则

这是 CLAUDE.md 最有价值的一类。

因为代码往往表达：

> 系统现在是什么。

但不会表达：

> 为什么必须这样。

---

举个例子。

代码：

```kotlin
data class Product(
    val price: Int
)
```

AI 可以看到：

```
price 是 Int
```

但是不知道：

```
price 单位是分，不是元。
```

于是可能生成：

```kotlin
price / 100
```

也可能生成：

```kotlin
price * 100
```

业务直接错误。

---

这种规则应该写：

```md
## Business Rules

- 所有金额字段均使用分作为存储单位。
- UI 展示金额前必须经过 MoneyFormatter。
```

因为它满足：

* 代码难以推断；
* 错误成本高；
* 长期有效。

---

再比如订单状态：

```kotlin
enum class Status {
    CREATED,
    PAID,
    CANCELLED
}
```

AI 不知道：

```
CANCELLED 状态只能由后台触发，客户端禁止主动修改。
```

这种也属于隐性知识。

---

## 四、第三类：团队开发约定

很多团队都有一些：

> 大家默认知道，但代码不会告诉作者的规则。

例如 Android 项目：

```text
所有 UI 状态必须通过 UiState 管理。
```

或者：

```text
禁止 Fragment 直接调用 Repository。
```

再比如：

```text
禁止 View 层直接创建 UseCase。
```

```text
所有业务逻辑必须经过 ViewModel。
```

```text
禁止 DataSource 被 UI 层直接引用。
```

代码可能允许：

```kotlin
fragment.repository.load()
```

但是团队约定不允许。

---

这种规则适合放：

```md
## Architecture Rules

- UI 层不得直接访问 Repository。
- 所有页面状态通过 ViewModel 暴露。
- 新增页面必须遵循现有 Feature 模块结构。
```

---

但是注意：

不要把普通代码规范全部塞进去。

例如：

```text
变量必须使用 camelCase。
```

这种更适合：

* IDE Inspection；
* Lint；
* Formatter；
* 静态检查。

因为：

AI 提醒 ≠ 自动约束。

---

## 五、第四类：工作流程

这一类非常容易误判。

很多人会写：

```md
修改代码后必须测试。

提交代码前必须检查。

开发完成必须运行 lint。
```

有没有问题？

没有。

但需要注意：

**流程规则必须具体。**

---

比较差：

```md
修改代码后运行测试。
```

问题：

什么测试？

全部？

部分？

怎么运行？

---

更好：

```md
## Verification

- 修改 Kotlin 代码后，根据模块运行对应单元测试。
- 修改 Compose UI 后运行 screenshot test。
- 修改数据库 Schema 后必须执行 migration test。
```

区别：

前者只是提醒。

后者可以执行。

---

## 六、第五类：容易反复犯错的问题

这是最适合进入 CLAUDE.md 的来源。

很多优秀规则，实际上不是设计出来的。

而是：

> AI 犯错很多次之后总结出来的。

例如：

第一次：

> Claude 修改了 generated 文件。

于是记录：

```md
不要直接修改 generated/
```

第二次：

> Claude 忘记更新 Mock。

于是：

```md
修改 API 后同步更新 Mock 数据。
```

第三次：

> Claude 修改数据库但是没有 Migration。

于是：

```md
Schema 变更必须包含 Migration。
```

这些规则都有一个特点：

它们来自真实反馈。

---

但是这里有一个陷阱。

不要：

> 每犯一次错，就永久增加一条规则。

应该问：

这个问题属于：

#### 偶然错误？

例如：

一次输入理解错误。

不用记录。

---

#### 系统性错误？

例如：

每次修改 API 都忘 Mock。

应该记录。

---

判断标准：

> 这个问题未来是否还会重复发生？

如果会，值得写！

---

## 七、第六类：告诉 AI 去哪里找答案

很多人忽略这一点。

CLAUDE.md 不一定需要保存所有知识。

有时候只需要告诉 AI：

> 权威答案在哪里。

例如：

```md
## References

- API 设计规范：
  docs/api-guideline.md

- 发布流程：
  docs/release.md

- 数据库规范：
  docs/database.md
```

这样的话，AI 需要时再读取。

而不是每次对话都加载全部内容。

---

这个思想非常重要：

> CLAUDE.md 应该是导航地图，不应该是整个图书馆。

---

## 八、一个真实项目里的 CLAUDE.md 应该长什么样？

例如：

```md
# Project Rules

## Architecture

- UI 层禁止直接访问 Repository。
- 新功能必须放入对应 feature module。

## Business Rules

- 金额统一使用分存储。
- 用户删除操作必须经过确认流程。

## Workflow

- 修改 API 后同步更新 Mock 数据。
- 修改数据库 Schema 必须创建 Migration。

## Verification

- Kotlin 修改运行对应单元测试。
- UI 修改检查截图测试。

## References

- API 文档：docs/api.md
- 发布流程：docs/release.md
```

它并不长。

但是每一条都有价值。

## 九、最终判断表

| 内容     | 示例              | 是否放 CLAUDE.md |
| ------ | --------------- | ------------- |
| 技术栈    | Kotlin、React    | ❌             |
| 目录结构   | app、data 模块     | ❌             |
| 业务规则   | 金额单位是分          | ✅             |
| 团队约定   | Repository 访问限制 | ✅             |
| 常见错误   | 不修改 generated   | ✅             |
| 测试流程   | 修改接口跑哪些测试       | ✅             |
| 一次性任务  | 今天不要改登录页        | ❌             |
| 版本信息   | 当前版本 1.2.3      | ❌             |
| 文档位置   | 去哪里找发布规范        | ✅             |
| 强制安全检查 | 防止密钥提交          | ❌ 更适合 CI      |

注意：

不是说安全规则不能写进 CLAUDE.md。

而是：

CLAUDE.md 只能提醒 Agent。

不能保证 Agent 一定遵守。

真正需要 100% 阻止的问题，例如：

- 密钥提交；
- 代码扫描；
- 发布检查；

应该交给 CI、Hook 或自动化工具。

这一点后续文章还会展开。

## 十、本篇真正需要记住的 5 句话

### ① CLAUDE.md 不是项目介绍文档

它记录的是：

> 工作规则。


### ② 不要写 AI 能轻易发现的信息

代码和配置已经存在的信息，不需要重复复制。


### ③ 优先记录隐性知识

尤其：

> 代码无法表达，但错误成本很高的事情。


### ④ 规则应该来自真实问题

不要提前幻想所有可能错误。



### ⑤ CLAUDE.md 是地图，不是图书馆

告诉 AI：

> 重要规则是什么，答案在哪里。

而不是：

> 把整个项目重新讲一遍。
