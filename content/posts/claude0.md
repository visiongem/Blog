最近整理 Claude Code 和 Codex 的项目规则时，发现一个很有意思的现象：

很多人第一次接触 Coding Agent 后，都会不断往 `CLAUDE.md` 里面添加规则。

AI 犯一次错，加一条；

忘一次流程，再加一条。

最后，本来为了帮助 AI 的文件，逐渐变成了一个没人敢删除的“规则仓库”。

因此今日份整理一下，这类文件应该记录什么，哪些内容不适合长期塞进去吧。

最先遇到的，通常是：

```text
CLAUDE.md
```

使用 Codex 时，则会接触到：

```text
AGENTS.md
```

两者的用途相近，但分别属于 Claude Code 和 Codex 的项目指令机制。不要默认它们的文件层级、优先级和语法完全一致。

它们解决的是一个很朴素的问题：

> **怎样让 AI 在开始干活之前，就知道这个项目有哪些必须遵守的规则？**

这听起来很简单，但真正使用一段时间之后，很容易遇到另一个问题：

> **CLAUDE.md 越写越长了。**

几个月以后，打开 CLAUDE.md：

```text
项目介绍
目录结构
技术栈
开发规范
测试规范
代码示例
历史问题
各种 Don't
各种 Must
……
```

最后变成了一本几十页的“AI 员工手册”。

问题是：

**规则越多，AI 就一定越听话吗？**

答案并不是。

## 一、先理解：CLAUDE.md 是什么

最简单的理解是：

> **CLAUDE.md 是项目提供给 Claude Code 的长期工作说明。**

这里的“长期”不是指永远存在，而是指它应该记录跨任务、跨时间仍然成立的约定。

例如项目根目录：

```text
my-project/
├── CLAUDE.md
├── src/
├── tests/
├── package.json
└── README.md
```

里面可以写：

```md
# Project Instructions

- 修改网络接口后，必须同步更新 Mock 数据。
- 不要直接修改 `generated/` 目录；修改源文件后运行生成命令。
- 根据改动范围运行相关测试或代码检查。
- API 相关修改必须同步更新对应测试。
```

当 Claude Code 在这个项目中工作时，这些内容可以作为它执行任务时的项目上下文和行为指引，但它不是 CI 或权限系统，不能替代自动化检查。

Anthropic 官方将 CLAUDE.md 归入 Claude Code 的 memory 机制，用于保存项目相关的长期指令，也建议使用它保存项目架构、编码规范和常见工作流程等团队共享指令。

所以，可以把它理解成：

> **在 AI 开始工作之前，项目提前告诉它：“在这里工作，需要知道这些事情。”**

---

# 二、但 CLAUDE.md 不是项目百科全书

这是学习 CLAUDE.md 最重要的一点。

很多人第一次使用 `/init` 之后，会得到一份看起来非常完整的 CLAUDE.md。

于是产生一个误区：

> “既然 AI 已经帮我整理出来了，那我把这些全部留下来不就好了？”

其实不是。

因为项目里的信息，适合放入指令文件的程度并不相同。

### 第一种：AI 可以自己找到的信息

例如：

```text
项目使用 Kotlin
项目有 app 模块
项目使用 Gradle
项目有 test 目录
项目存在 Retrofit
```

这些东西通常可以直接从代码、配置文件和目录结构中找到。

例如：

```text
build.gradle.kts
settings.gradle.kts
gradle/libs.versions.toml
app/src/
```

AI 完全可以通过探索项目获得这些信息。

Claude Code 本身就被设计成可以直接探索代码库，根据任务寻找相关文件，而不是要求开发者把整个项目手动塞进上下文。

所以：

> **能被 Agent 可靠发现、且不容易误判的客观事实，通常不必重复写进 CLAUDE.md。**

---

# 三、真正值得写进去的是什么？

真正值得写进 CLAUDE.md 的，通常是：

> **Agent 难以可靠确认，但又会影响正确性、验证流程或安全性的内容。**

可以先记住三个判断维度：

| 条件 | 建议 |
| --- | --- |
| Agent 能直接发现 | 不一定需要写 |
| Agent 不容易发现 | 值得考虑写入 |
| 判断错误的成本高 | 优先写入 |

举个简单的例子。

假设项目里面有一个价格字段：

```kotlin
price
```

AI 从代码里可能知道：

```text
price 是商品价格
```

但是它未必知道：

> 所有 `price` 在 UI 层展示时都必须包含税费。

这就是项目的**隐性规则**。

再比如：

```text
修改 API 后必须同时修改 Mock 数据。
```

代码里可能没有一个地方明确写着：

```text
修改 API → 修改 Mock
```

但团队一直这么做。

这种信息就很适合写进 CLAUDE.md。

因此可以建立一个非常重要的判断标准：

| 信息 | 是否适合 CLAUDE.md |
| --- | --- |
| 项目使用 Kotlin | ❌ 通常不需要 |
| 项目有 app 模块 | ❌ 通常不需要 |
| 使用 Retrofit | ❌ 通常不需要 |
| 修改 API 必须同步 Mock | ✅ |
| 某个目录禁止人工修改 | ✅ |
| 发布前必须执行某项检查 | ✅ |
| 某业务字段有特殊含义 | ✅ |
| 常用构建、测试命令 | ✅ 如果容易选错或需要频繁使用 |
| 某个团队约定无法从代码推断 | ✅ |

其中“必须执行的检查”这类规则，最好写清楚触发条件和具体命令；需要机械保证的要求，则应该交给 CI、Hook、测试或构建系统。

一句话：

> **CLAUDE.md 应该优先记录稳定、关键、可执行的约定，而不是复制整个项目。**

---

# 四、什么时候不应该写进 CLAUDE.md？

同样重要。

如果一条信息属于下面这些类型，就应该谨慎考虑。

### 1. AI 随便搜索就能找到

例如：

```text
Retrofit 定义在哪里
```

不一定需要写。

### 2. 很快就会变化

例如：

```text
当前版本是 1.2.3
```

如果版本经常变化，就不适合作为长期规则。

### 3. 只针对一次任务

例如：

```text
今天先不要修改 LoginActivity。
```

这更适合直接告诉 AI，而不是永久写入 CLAUDE.md。

### 4. 只针对某一个目录

例如：

```text
前端页面修改后必须截图检查。
```

如果只有 `frontend/` 需要这条规则，那么应该按照工具支持的目录级机制，把它放到更局部的位置。若这条检查必须强制执行，则应考虑使用 CI 或 Hook。

这一部分我们后面专门讲：

> **CLAUDE.md、Rules、Skill、Hook 应该如何分工。**

# 五、为什么内容堆得越多，可能越糟？

我们假设有一个非常简单的 CLAUDE.md：

```md
# Rules

1. 根据改动范围运行相关检查。
2. 不要修改 generated/。
```

这很好。

后来遇到一个问题：

> Claude 有一次忘记运行测试。

为了避免再次漏测，又加了一条更宽泛的规则：

```md
3. 任何修改都必须运行所有测试。
```

又有一次：

> Claude 使用了错误的 API。

于是：

```md
4. 不要使用旧 API。
```

继续……

最终，规则堆到了几十条。

表面上看：

> **规则越来越完善。**

实际上却可能出现一个问题：

> **真正重要的规则被大量次要规则淹没了。**

而且 AI 每次执行任务时，都需要综合：

```text
系统指令
+
项目规则
+
当前任务
+
代码上下文
+
工具结果
+
历史对话
```

低价值、重复、冲突或过期的规则，会增加 Agent 的判断成本。

典型的例子就是这种：

```md
项目有三个模块。

app 模块负责 Android UI。

network 模块负责网络。

data 模块负责数据。

项目使用 Kotlin。

项目使用 Gradle。

……
```

这些内容看起来没有错，但每一次都作为“规则”被带进去，真的值得吗？很多时候并不值得。

这并不意味着“Prompt 越短越好”，而是：

> **不要让无意义的指令占据本来可以用于真正任务的上下文。**

所以也不要用文件长度来衡量 CLAUDE.md 的质量。看到别人有一份 500 行的 CLAUDE.md，自己只有 30 行，不需要觉得“是不是太简单了”。如果这 30 行全是必须知道的规则，而别人的 500 行里有大量项目介绍、重复规则和过期规则，那 30 行反而更有价值。

应该综合考虑：

> **规则价值、可执行性和维护成本。**

# 六、那 `/init` 是干什么的？

第一次接触 Claude Code 时，可以使用：

```text
/init
```

Claude Code 会根据项目情况帮助创建一份 CLAUDE.md。

Anthropic 官方文档目前仍然把 `/init` 作为初始化项目 CLAUDE.md 的方式，并建议其中可以记录常用的构建、测试、代码检查命令，以及项目特有的重要架构模式等。

但这里有一个非常重要的认识：

> **`/init` 生成的是起点，不是最终答案。**

很多团队真正成熟的 CLAUDE.md，往往不是第一次生成出来的，而是在长期使用过程中不断删除和提炼出来的。

可以把它理解成：

```text
/init
  ↓
生成初稿
  ↓
人工审查
  ↓
删除冗余、重复和过期的信息
  ↓
补充项目隐性规则
  ↓
得到真正有价值的 CLAUDE.md
```

而不是：

```text
/init
  ↓
生成
  ↓
提交 Git
  ↓
永远不再修改
```

# 七、用三个问题判断每条规则

以后看到 CLAUDE.md 里面的一条内容，可以连续问三个问题：

1. Agent 能否可靠确认这件事？

2. 如果判断错误，代价是否较高？

3. 这条内容是否适用于大多数相关任务？

如果它难以确认、误判代价高，而且会反复影响任务，就很适合写入项目指令。

例如，下面两条内容的优先级就不同：

```text
项目使用 Kotlin
```

AI 能找到。

```text
金额全部以“分”为单位
```

前者通常可以从配置和代码中确认，后者却可能影响业务正确性，值得明确写出。

# 八、把 CLAUDE.md 想象成“员工入职第一天”

我觉得这是理解它最好的比喻。

假设来了一个非常聪明的新员工。

不可能第一天就把公司的：

```text
5000 页 Wiki
1000 页历史文档
所有代码
所有会议记录
所有项目背景
```

全部塞给他。

真正希望新员工第一天知道的是：

```text
1. 我们这个团队最重要的事情是什么？

2. 有哪些绝对不能犯的错误？

3. 有哪些特殊规则？

4. 遇到问题应该去哪里找答案？

5. 什么情况下必须停下来确认？
```

CLAUDE.md 也是一样。

它不是：

> **“把整个项目解释给 AI。”**

而是：

> **“告诉 AI，在这个项目里工作时，哪些事情特别重要。”**

这两个目标完全不同。

---

# 九、这一篇真正需要记住的 5 句话

如果这一篇只记住五句话，我建议就是下面这五句：

### ① CLAUDE.md 是项目给 AI 的长期工作说明

它不是用来完整介绍项目的百科全书。

### ② 不要把项目百科全书塞进去

AI 本身就可以探索代码库。

### ③ 优先记录“隐性规则”

尤其是：

```text
代码看不出来
+
AI 必须知道
```

这样的信息。

### ④ `/init` 只是起点

生成之后要人工审查，而不是生成完就结束。

### ⑤ CLAUDE.md 的目标不是“越完整越好”

真正的目标是：

> **用高价值、可执行、范围匹配的规则，让 Agent 更稳定地完成项目工作；需要强制保证的要求交给自动化系统。**

这也是后面所有内容的基础。
