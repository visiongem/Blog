Jake Wharton 在这场两个多小时的访谈里，谈到了推动 Kotlin 进入 Android 的经历、离开 Google 和 Cash App 的原因，也解释了自己为什么拒绝 AI 编程，以及为什么仍然愿意花时间维护开源项目。

**原视频：** [Kotlin 2026: Layoffs, AI, Google — Is the Golden Age Over? Jake Wharton Explains](https://www.youtube.com/watch?v=9WjPdgOK-68)

本文根据视频文稿按主题整理，属于中文访谈摘要，非逐字翻译，不代表整理者立场。文中的就业观察、公司评价和 AI 预测均保留为受访者观点；录制时提及的数据与行业事件未逐项独立核验。

**履历与名称说明：** 根据 [Jake 本人的简历](https://jakewharton.com/r%C3%A9sum%C3%A9/)，他于 2012 年 3 月至 2017 年 7 月在 Square（Cash App）工作，2017 年 8 月至 2020 年 5 月任职 Google，随后回到 Cash App，工作至 2025 年 11 月。Cash App 是公司旗下的业务与产品品牌；母公司 Square, Inc. 于 2021 年更名为 Block, Inc.，Square 与 Cash App 保留各自品牌。本文沿用访谈中的“在 Cash App 工作”，指其在该业务团队的任职经历。[公司更名公告](https://squareup.com/us/en/press/square-changes-name-to-block)

## 1. Kotlin 能进入 Android，靠的是渐进迁移

从 [00:53](https://www.youtube.com/watch?v=9WjPdgOK-68&t=53s) 开始，Jake 回顾了 Kotlin 出现时的环境。

当时 Java 的语言演进比较缓慢，Android 开发者想使用更现代的语言特性。社区有人尝试 Scala，也有人尝试 Groovy。Kotlin 进入了这个窗口期，又有 JetBrains 提供 IDE 和工具支持，开发者采用它时不用从零搭建生态。

他特别强调 Java 互操作的重要性。团队可以继续使用已有的 Java 库，保留旧代码，只在局部加入 Kotlin。一个新语言要进入成熟项目，这种迁移方式能减少许多阻力。

他在 Square 为引入 Kotlin 写过一份论证文档，后来将其公开。文档讨论的问题并不局限于 Square，也帮助其他团队向管理者解释为什么值得采用 Kotlin。

Google 后来正式支持 Kotlin，同样经历了谨慎的过渡。Jake 说，Android 团队已经围绕 Java 建设多年，对一个刚稳定不久的新语言有所顾虑是合理的。早期的做法包括先为 Java 库提供 Kotlin 配套扩展，再逐步深入，而非要求所有项目立即重写。

### 为什么他又离开 Google？

在 [08:52](https://www.youtube.com/watch?v=9WjPdgOK-68&t=532s)，他的解释很直接：去 Google 原本就带着阶段性目标。他希望帮助 Kotlin 成为 Android 的正式开发语言，之后回到产品开发中，使用自己参与建设的工具。

他原计划待两年，临近离开时又获批了一个想做的项目，因此多留了九个月。他喜欢写工具和库，也想亲自体验这些工具在真实产品里的作用。

## 2. 在 Android 岗位中，Kotlin 已经成为基础要求

在 [11:17](https://www.youtube.com/watch?v=9WjPdgOK-68&t=677s)，Jake 谈到离开 Cash App 后找工作的经历：岗位仍然存在，但找工作的难度与几年前不同。他自己也花了更多精力，只是因为主动离职、有积累，可以更挑剔地选择公司。

主持人问到美国资深 Kotlin 工程师的薪资时，他提到自己看到的一些岗位在年薪 20 万美元及以上，并可能附带股权；他同时强调，也有很多岗位低于这个水平。这些数字来自他个人接触到的岗位。

到了 [14:32](https://www.youtube.com/watch?v=9WjPdgOK-68&t=872s)，他认为 Kotlin 的普及改变了它的职业价值：过去掌握 Kotlin 可以让候选人与众不同，如今 Android 开发者通常已经被期待掌握它。Compose UI 也在经历类似变化。

在他看来，Kotlin 已经普及，掌握它本身不再稀缺；多平台等更深入的使用经验，仍可能成为候选人的差异化优势。

## 3. 离开 Cash App 后，他用九条标准选择下一份工作

在 [15:54—41:07](https://www.youtube.com/watch?v=9WjPdgOK-68&t=954s)，主持人逐项询问了 Jake 求职时列出的九条标准，以及他最终选择公司的原因。

| 标准 | 他在意的事情 |
| --- | --- |
| 不加入以 AI 为核心业务的公司，不接受强制 AI 编程 | 关注训练数据伦理、软件质量，以及工程师选择工具的自主权 |
| 不做加密货币业务 | 认可密码学，但反对他眼中依赖投机和价值抽取的加密货币商业模式 |
| 远程工作 | 保留照顾家庭和安排时间的灵活性，也愿意每年线下见面几次 |
| 支持开源 | 公司使用他人的开源成果，也应愿意贡献或开放自己的成果 |
| 客户优先于股东 | 产品应持续给客户带来价值，不能只围绕投资者收益调整 |
| 重视人，反对剥削性经营 | 关注零工劳动者的实际成本、保障和议价能力 |
| 小而专注 | 希望团队聚焦产品，工程师能接触较完整的工作，而非局限于很窄的一块 |
| 多元、公平与包容 | 机会与待遇不应简单取决于出生地、性别、肤色等个人难以控制的条件 |
| 工作与生活有边界 | 手机不安装工作聊天和代码审查工具，避免随时在线成为默认要求 |

他对商业模式的要求尤其严格。他希望公司有可持续的收入来源，不必等补贴结束后，再通过涨价、限制功能等方式向用户收回成本。按他的估计，这一要求排除了绝大多数候选公司，也意味着他需要接受降薪的可能。

### 资深工程师的行为会变成团队的隐形规则

谈到工作边界时，他举了一个具体例子：自己周末审查 PR，可能只是为了补偿周中没工作的时间。但新人看不到这些背景，只会看到一位资深同事在周日深夜处理工作。

新人很容易据此认为，公司期待大家随时响应。因此，他后来选择不在手机上安装工作聊天和代码审查应用，也希望用自己的行为说明：下班后断开连接是正常的。

### 为什么选择 Skylight？

根据访谈，他在 2026 年 2 月加入 Skylight。这家公司做面向家庭的设备，用来管理日历、孩子的活动、购物清单、餐食和家务。他自己就是目标用户，也使用过产品。

这份工作还让他有机会接触 Android 硬件、AOSP，以及应用商店之外的分发方式。对一个写了多年 Android 应用的人来说，这些都是仍有探索空间的工作。

**Skylight 也有大语言模型（LLM）功能。** Jake 解释，这些功能完全可选，他认为其用途适当，产品也没有整体转向聊天机器人。主持人问他是否为这份工作妥协了自己的标准，他回答自己不这么认为。

开源方面，Skylight 当时尚未开展多少工作，但愿意尝试，也认可他继续承担现有开源项目的维护责任。这些项目中的一些同样用于公司的产品。

## 4. 他为什么拒绝 AI 编程？

在 [47:15](https://www.youtube.com/watch?v=9WjPdgOK-68&t=2835s)，主持人问他是否用过 AI Agent 写代码，他回答没有。他也承认，自己有意采取鲜明的立场，希望大家考虑工具背后的问题。

他的反对主要涉及三个方面。

**首先是训练数据与创作者权益。** 他质疑一些模型训练对代码许可证、版权和创作者意愿的处理。

**其次是工程师的自主权。** 在他的经验里，Kotlin、IDE 或构建工具往往由工程师尝试后推动采用。他反感管理层直接规定开发者必须使用某种 AI 工具，尤其当这种要求又与裁员同时出现时。

**还有成本与依赖风险。** 他担心公司按补贴阶段的工具价格估算收益，先裁掉工程师，随后却失去独立完成工作的能力。一旦供应商调整价格，团队可能已无法轻易退出。

他预测，这种路径会导致长期软件质量下降；随着补贴减少，AI 工具的使用成本也会明显上升。

### 他仍然区分“负责任”和“不负责任”的使用

在 [48:34](https://www.youtube.com/watch?v=9WjPdgOK-68&t=2914s)，Jake 把伦理问题和使用方式分开讨论。

他所说的负责任使用，是让工具辅助自己已有的工程能力。例如减少重复操作、加快熟悉任务的执行；开发者仍然理解产出，也能在工具不可用时继续工作。

他认为风险较高的做法，是让工具生成超出自身理解和维护能力的系统。代码暂时能运行，不代表使用者能判断边界条件、定位故障，或承担之后的修改。

因此，他关心的问题包括：离开这个工具后，你还能不能完成工作？代码出现问题时，你是否能解释和修复它？

谈到“如果 AI 很快比你写得更好怎么办”，他的回答带着个人处境：可以去更小的公司、赚更少的钱，继续做让自己开心的工作。他明确承认，职业积累让自己拥有这种选择，许多人没有同样的条件。

他对 AI 很快全面超过工程师的设想持怀疑态度，并提到用模型生成内容反复训练可能带来的“模型坍塌”风险。谈到相关研究时，他没有确认具体出处。他也承认，现有模型的能力已经很强，但认为生成的代码仍需要人调试。

## 5. AI 会写样板代码，Kotlin 还有什么价值？

在 [53:39](https://www.youtube.com/watch?v=9WjPdgOK-68&t=3219s)，主持人提出：既然 AI 能生成 Java 样板代码，Kotlin 减少代码量的优势是否已经消失？

Jake 的回答把注意力放到了代码的整个生命周期。

写代码之前，工程师要理解问题、决定模块边界、建立业务模型。写完之后，还要处理缺陷、需求变化和持续重构。最初输入多少字符，只占其中一部分。

Kotlin 的类型系统、可空性表达、IDE 和重构工具，在这些长期工作中仍然有价值。即使大量代码由工具生成，团队依然需要阅读它、理解它，并安全地修改它。

他也承认，减少样板代码是早期推广 Kotlin 时很好展示的卖点，但这不足以解释一门语言能否长期服务大型代码库。

## 6. 他喜欢 Kotlin，也直言 Swift 和 Rust 有值得学习的地方

从 [56:57](https://www.youtube.com/watch?v=9WjPdgOK-68&t=3417s) 开始，访谈讨论了 Java、Swift、Rust 与 Kotlin 的不同取舍。

### Java 的进步值得 Kotlin 学习

Jake 肯定 Java 加快发布节奏、引入实验性特性，以及语言和虚拟机协同演进的工作。

早期 Kotlin 为兼容旧 JVM，需要把新语言特性转换成旧字节码能够表达的结构。Java 则有机会连同运行时一起调整。他希望 Kotlin 持续吸收底层平台的新能力。

他仍然很看重 Kotlin 对可空性的建模。业务中总会有“没有值”的情况，语言能够让调用方在编译期面对这种可能性，就能减少把问题留到运行时才发现的机会。

### 他更欣赏 Swift 的部分语言设计

Jake 认为，Swift 的显式错误处理和值类型设计有吸引力。相较之下，Kotlin 的突出优势还包括 JVM 库生态、开源文化，以及 IntelliJ 等开发工具。

他强调，语言设计之外，库、构建、静态分析和重构工具也会影响一门语言能否在生产项目中得到广泛采用。

### 他最希望 Kotlin 改善的是错误建模

在 [1:32:34](https://www.youtube.com/watch?v=9WjPdgOK-68&t=5554s)，他说自己过去最不喜欢声明默认使用 `public` 可见性，更希望默认是 `internal`；如今他更在意异常和错误处理。

Kotlin 函数的签名通常不会完整说明它可能怎样失败。一次看起来普通的调用，内部可能访问网络或数据库，然后抛出调用者没有预料到的异常。

他用地铁里的应用和失去响应的售票设备举例：开发环境的网络通常很好，真实用户却会断网、重复点击，或在意外状态下继续操作。他希望语言能像表达可空性一样，迫使开发者考虑失败，决定就地处理还是交给上层。

这也是他欣赏 Rust 的原因。错误、所有权、借用和资源释放等概念，与他多年踩坑之后形成的判断相符。他同时承认 Rust 学习成本很高，自己也还不熟练。

至于 Gradle，他认为一个长期问题是早期偏重脚本易写和语法便利，后来为正确性、增量构建与性能补课，导致使用者持续经历迁移成本。

## 7. KMP 的价值在于按需要共享，并保留各平台的体验

在 [1:06:30](https://www.youtube.com/watch?v=9WjPdgOK-68&t=3990s)，Jake 明确说了自己不会优先选择 Kotlin 的场景。

如果从零开发一个只面向 Web 的应用，他不会先选 Kotlin 和 Compose UI；只做 iOS 时，他倾向于 Swift；他也认为 Kotlin 不太适合资源紧张的微控制器。

如果已有 Kotlin 代码，需要把业务逻辑复用到别的平台，情况就不同了。他欣赏 Kotlin Multiplatform（KMP）能让团队决定共享范围，例如数据同步、业务规则和其他容易重复实现出错的部分。

他在 Cash App 推动共享代码时，希望给 iOS 工程师腾出时间，专注动画、交互和平台体验。他明确表示，当时的目标是让 iOS 工程师专注平台特有的体验，而非替代他们。

### 为什么他偏好原生 UI？

在 [1:23:11](https://www.youtube.com/watch?v=9WjPdgOK-68&t=4991s)，他给出了一段很具体的用户视角。

产品团队可能希望同一个产品在 Android、iOS 和 Web 上完全一致。但很多用户日常是在同一台设备上的多个应用之间切换。他们已经熟悉这个平台的滚动、按钮反馈和交互方式。

因此，他更看重应用与所在平台的其他应用保持一致。共享业务规则后，各平台仍然可以保留自己的表现方式。

他对 Flutter 的批评很尖锐，更认可 React Native 尝试使用平台原生 UI 的方向。不过，他也承认两者都可以做出好应用。

## 8. Cash App 的实践：Compose Runtime、Redwood 与 Zipline

在 [1:11:30](https://www.youtube.com/watch?v=9WjPdgOK-68&t=4290s)，Jake 介绍了在 Cash App 的跨平台开发经历。

Cash App 有时需要根据监管要求，短期内修改文案、界面或部分业务行为。不断打断应用商店发布节奏处理这些修改，给团队带来了负担。

他们构建了一套可更新部分业务逻辑和 UI 行为的方案：使用 Kotlin 编写共享逻辑，编译成 JavaScript，在 Android 和 iOS 内嵌的 JavaScript 引擎中执行，再驱动各端的原生界面。

**他特意区分了 Compose 与 Compose UI：这套方案使用 Compose 的运行时机制，并没有把各端界面统一交给 Compose UI 绘制。**

共享代码描述的是设计系统里的组件语义。例如“这里需要一个主按钮”，而按钮的颜色、圆角、触摸反馈，由各平台实现负责。

| 部分 | 在这套方案中的职责 |
| --- | --- |
| Kotlin 共享代码 | 表达共享逻辑及界面行为 |
| Compose Runtime | 支持声明式逻辑与状态变化的组织 |
| Redwood | 将共享的组件描述连接到各端 UI 实现 |
| Zipline | 提供独立的、可更新的 Kotlin/JS 代码运行机制 |
| 原生设计系统 | 决定具体组件在各平台如何呈现和交互 |

这种方案需要较多前期投入：团队需要先有设计系统和组件抽象，才能让共享代码使用这些语义组件。Jake 明确说，它不是从零开始就能轻松套用的方案。

按他的回顾，这套技术进入过重要的生产页面，但后来公司方向变化，项目逐步收缩。相关工具和库已经开源，因此成果仍然保留下来。

### 为什么坚持做库？

在 [1:27:10](https://www.youtube.com/watch?v=9WjPdgOK-68&t=5230s)，他解释了自己偏好库的原因。

库要求使用者思考如何集成，也常常需要编写胶水代码。他看重的回报是：未来需求、语言或技术偏好改变时，可以更局部地替换组件。

Redwood 与 Zipline 就是分开的。团队可以使用 Redwood 而不接入动态更新，也能把 Zipline 用于其他用途。两者组合需要额外工作，却不必让一个组件控制整个应用的结构。

他认为，对于已经维护十几年、经历过多次技术迁移的代码库，这种边界能帮助团队逐步替换组件。

## 9. 使用开源依赖，也意味着承担维护责任

在 [1:53:18](https://www.youtube.com/watch?v=9WjPdgOK-68&t=6798s)，主持人问他如何看待依赖风险和 fork。

Jake 的出发点是：用户收到的产品包含了你的代码，也包含第三方库。用户不会因为问题发生在依赖里，就认为产品团队没有责任。

因此，他希望开发者把依赖当成产品的一部分：关注项目方向、理解变更，在需要的时候参与修复。他反对那种只在构建文件里添加一行依赖，却默认维护者必须长期满足自己全部需求的态度。

### 有了 AI，为什么还需要公共库？

他的回答强调共同维护的收益。

上游修复了一个罕见缺陷，许多使用者可以一起受益。上游改善性能，依赖它的项目也能获得提升。即使某个缺陷在自己的项目里暂时不会触发，未来重构时也可能遇到，而公共库可能早已解决它。

让每个项目分别生成一份相似代码，并不会自动获得这种持续积累的修复。

### 开源需要支持，支持不只有捐款

在 [2:03:17](https://www.youtube.com/watch?v=9WjPdgOK-68&t=7397s)，Jake 区分了公司雇员在工作时间维护的项目，以及个人业余项目。

他指出，两者在外观上都可能只是一个 GitHub 仓库，但背后的维护资源差别很大。一个个人项目变成企业的关键依赖之后，维护者可能逐渐从兴奋变成负担沉重。

他希望企业提供资金，也认为代码贡献、修复缺陷、分类处理问题报告（issue） 等工作有价值。这些投入能减轻维护者的日常负担。开源带来的认可令人高兴，持续的维护却需要时间和收入。

他也不赞成强迫所有工程师公开工作。有些人喜欢社区交流，有些人不愿承担公开身份、争论和持续响应的压力，两种选择都应被尊重。

## 10. 保持成长：通过其他语言学习不同的思路

从 [1:37:38](https://www.youtube.com/watch?v=9WjPdgOK-68&t=5858s) 开始，Jake 谈如何避免倦怠。

Android 早期快速发展，每年都有新东西可学。随着平台成熟，他转向硬件、微控制器，以及 Rust、Swift、Zig、C 等语言寻找兴趣。

他给开发者的建议是，学第二种语言时，不必把目标定成达到与主业相同的熟练程度。可以先体验它如何表达问题，再把有用的思路带回来。

例如，学过 Rust 的所有权之后，即使继续写 Kotlin，也会更主动地考虑：资源归谁管理？参数传入函数后，调用方是否还能修改？谁负责关闭连接？这些隐含约定有没有可能在半年后的重构中被破坏？

他还建议将学习与真实需求结合。他不喜欢家里的灌溉控制器，就想自己做一个。这件事给学习嵌入式语言和电路提供了具体动力，比单纯要求自己“应该学 Rust”更容易坚持。

这是他的个人方式。他同样支持下班后完全离开电脑，通过与编程无关的活动恢复精力。

## 11. 一门语言应该能够离开创造者继续发展

在 [2:07:32](https://www.youtube.com/watch?v=9WjPdgOK-68&t=7652s)，主持人问 Kotlin 是否能在最初的创造者离开后继续演进。

Jake 认为，这正是一门成熟语言应该具备的能力。一个人花十年做成一件事之后，当然可以去做别的事情。共享责任、建立组织和社区参与机制，有助于让项目持续下去。

谈到自己对 Kotlin 的影响，他没有把语言成果归功于个人。他提到曾推动团队使用穷尽式 `when` 检查，也持续关注错误处理等提案，希望真实代码库里的经验能进入语言设计讨论。

他鼓励普通开发者阅读提案、参与讨论。许多业务代码无法公开，语言设计者看不到所有使用方式；一条解释实际问题的反馈，也可能有帮助。

最后，他说 Kotlin 没必要永远扩张到所有场景，语言也不必永远存在。但对他个人而言，自己在 Kotlin 上投入了很多，仍然乐于继续围绕它工作。
